## 2. 项目背景

1. 本项目为个人开发项目，用于学习、验证和理解 Agent 智能体相关技术及架构特点，并实现本需求规定的能力。
2. 本项目不以产品化或生产级交付为目标，不要求建设企业级治理、复杂审批、复杂交接或高可用体系。
3. 当前已有基础设施及业务系统均由同一开发者维护，阶段管理以明确目标、关键节点和完成条件为主。
4. 项目优先保证：

   - 架构边界相对完整。
   - Agent 生成及工具调用能力可运行。
   - 知识库和业务数据查询链路能够端到端打通。
   - 后续新增能力不破坏现有能力结构。
5. 即使属于个人非生产项目，仍应保留必要的身份认证、业务域授权、失败处理、契约一致性和基本测试，不以简化为由绕过业务系统权限。

## 3. 建设目标

建设一个单体 Agent，使其能够理解用户的自然语言问题，选择合适的查询能力，调用知识查询能力或业务系统，并将结果整理为自然语言答案。

第一阶段提供三类能力：

1. 知识库查询。
2. Employee 域结构化数据查询。
3. Transaction 域结构化数据查询。

其中：

- 结构化数据可以由业务服务内部通过数据库、Elasticsearch 或其他存储实现，但 Agent 不直接访问业务数据库或业务域 ES 索引。
- 知识查询应复用当前已有的 `es-query-service`、Elasticsearch 向量索引和测试数据，并补齐面向 Agent 的问题改写、多知识域、多路召回与重排、证据化答案摘要能力。

## 4. 总体范围

### 4.1 本期范围

- 单个 Agent 运行实例。
- 用户自然语言输入理解。
- 查询能力选择。
- 知识查询问题改写。
- 多知识域选择和受控路由。
- 多路召回、融合与重排。
- 基于检索证据的答案摘要。
- Employee 域有限查询动作。
- Transaction 域有限查询动作。
- 查询参数生成、校验和调用。
- 查询结果整理与回答生成。
- 用户 JWT 透传。
- 业务系统角色校验。
- 查询动作配置。
- 基本错误处理、日志及测试。

### 4.2 非本期范围

- Multi-Agent。
- Agent 间通信、协商及任务分配。
- 跨业务域聚合查询。
- 业务写入、提交、审批或状态变更。
- 工作流编排。
- 定时或无用户上下文的后台 Agent 任务。
- 文档录入、切分、文档侧向量化和知识库索引建设；查询文本向量化属于本期知识查询范围。
- 任意 SQL 查询。
- 任意 Elasticsearch DSL 查询。
- 动态插件平台。
- 配置热更新。
- 生产级高可用、复杂审计、复杂交接和企业级权限治理。

## 5. 功能需求

### FR-01 单体 Agent

1. 系统应运行一个单体 Agent。
2. Agent 应负责：

   - 接收用户问题。
   - 判断应使用的查询能力。
   - 生成符合目标能力约束的查询参数。
   - 调用相应 Adapter。
   - 整理调用结果并生成回答。
3. Agent 不得包含 Employee、Transaction 的业务规则。
4. Agent 不得直接访问业务数据库或业务域 ES 索引。

### FR-02 知识库查询

1. 应复用当前已有的 `es-query-service`、Elasticsearch 向量索引和测试数据，不额外建设独立部署的 `knowledge-service`。
2. 应在单体 Agent 内建设知识查询能力，并通过独立的 `agent-knowledge-adapter` 调用 `es-query-service` 的受控只读检索接口。
3. 知识查询至少应具备：

   - 问题改写：根据原始问题生成保持原意、适合检索的查询表达。
   - 多知识域：从已注册且启用的知识域中选择一个或多个相关知识域；知识域是受控的知识集合，不等同于 Employee、Transaction 等业务域。
   - 多路召回与重排：至少支持关键词召回和向量召回，完成候选去重、融合及重排。
   - 答案摘要：仅基于检索证据生成答案摘要，并保留可追踪的证据来源。
4. 知识查询动作内部可以执行多知识域、多路检索，但在 Agent 能力层仍属于一个 `knowledge.query` 查询动作，不构成跨业务域聚合或工作流。
5. 模型不得直接生成或执行任意索引名、Elasticsearch DSL、动态 URL、写入、删除、批量索引或重建操作。
6. `es-query-service` 只负责类型化、只读、确定性的检索原子能力和结果返回，不负责问题改写、知识域意图判断、模型重排或答案摘要。
7. 本期不建设文档录入、文档处理、文档侧向量化或索引生命周期管理功能。
8. 当没有足够检索证据、召回失败或重排失败时，Agent 应明确说明，不得编造检索结果或答案。
9. 知识查询实际效果应在完整链路打通后，通过代表性问题对问题改写、召回、重排和答案结果进行验证。

### FR-03 Employee 域查询

1. Employee 域数据由 `employee-service` 负责管理。
2. Agent 应通过 `agent-employee-adapter` 调用 `employee-service` 的已有对外接口。
3. 应优先复用已有查询接口。
4. Agent 和 Adapter 不得直接访问 Employee 数据库或 Employee ES 索引。
5. Employee 查询应限制在业务域明确允许的有限查询动作内。
6. 如果已有接口不能满足必要查询能力，应先说明缺失接口、影响范围和建议契约，经确认后才能追加业务接口。

### FR-04 Transaction 域查询

1. Transaction 域数据由 `mq-procedure-service` 负责管理。
2. Agent 应通过 `agent-transaction-adapter` 调用 `mq-procedure-service` 的已有对外接口。
3. 应优先复用已有查询接口。
4. Agent 和 Adapter 不得直接访问 Transaction 数据库或 Transaction ES 索引。
5. Transaction 查询应限制在业务域明确允许的有限查询动作内。
6. 本期不调用聚合、写入、更新、删除或业务提交接口。
7. 如果已有接口不能满足必要查询能力，应经确认后才能追加业务接口。

### FR-05 Adapter 模块

1. Adapter 应作为 Agent 工程内部代码模块，与 Agent 一起构建和运行，不单独部署为微服务。
2. 首期至少包含：

   - `agent-knowledge-adapter`
   - `agent-employee-adapter`
   - `agent-transaction-adapter`
3. Adapter 可以负责：

   - Agent 查询参数与业务接口请求之间的转换。
   - 业务响应到统一能力结果的转换。
   - 参数边界校验。
   - 协议异常和业务错误的标准化。
   - 用户 JWT 透传。
   - Knowledge Adapter 将受控知识域和检索请求转换为 `es-query-service` 的只读检索请求。
4. Adapter 不得负责：

   - 用户角色授权判断。
   - 业务域权限规则维护。
   - Employee 或 Transaction 业务规则。
   - 直接数据库或 ES 查询。
   - 将模型生成的任意索引名、ES DSL 或索引管理操作透传到 `es-query-service`。
   - 绕过业务系统返回的 `401/403`。
   - 使用配置模拟不兼容的公共接口契约。

### FR-06 有限查询动作

1. 每个业务域应定义 Agent 可以调用的有限查询动作集合。
2. 每个查询动作应具备稳定标识、业务含义、输入约束和结果语义。
3. Agent 只能从已注册且已启用的查询动作中选择。
4. 不得由模型直接生成任意 URL、SQL、ES DSL、类名或方法名执行。
5. Employee 和 Transaction 的查询动作应相互隔离。
6. 本期不提供跨域聚合动作。
7. 知识查询可以在单个 `knowledge.query` 动作内部访问多个已注册知识域，但不得自动扩展到 Employee 或 Transaction 业务域。

## 6. 查询动作配置需求

### CFG-01 配置归属

1. Employee、Transaction Adapter 应分别管理本业务域的查询动作配置。
2. Knowledge Capability 应管理知识查询策略配置，Knowledge Adapter 应管理逻辑知识域到受控索引或别名的映射及检索边界配置。
3. Agent 核心负责加载和注册能力，不维护知识域、Employee、Transaction 的具体规则。
4. 配置应采用强类型绑定，并在启动时完成校验。

### CFG-02 可配置内容

配置可以包含：

- 动作启用状态。
- 动作名称、别名和简要说明。
- 知识域启用状态、稳定标识、描述及其受控索引或别名映射。
- 知识查询允许使用的召回路径、候选上限、重排上限和必要策略开关。
- 允许使用的过滤条件。
- 允许使用的排序条件。
- 最大分页大小。
- 最大查询时间范围。
- 调用超时。
- 服务发现名称或环境相关地址。
- 必要的查询策略开关。

### CFG-03 不允许配置化的内容

以下内容必须由代码和公共契约保证：

- 请求和响应类型。
- Adapter 处理器绑定。
- 业务字段转换逻辑。
- 业务接口的稳定语义。
- 错误转换规则。
- 身份认证和授权规则。
- 任意 SQL、ES DSL、动态 URL 或可执行类名。
- 由模型直接指定的物理索引名称、写入、删除、批量索引或重建行为。

### CFG-04 配置变更方式

1. 第一阶段不要求配置热更新。
2. 配置变更后允许通过重启 Agent 生效。
3. 配置错误应在启动阶段失败，不得带着无效配置继续提供相应能力。
4. 公共接口发生不兼容变化时，必须修改 Adapter 代码、契约测试及相关配置，不能仅通过配置规避。

## 7. 身份与权限需求

### SEC-01 用户身份

1. Agent 接收的用户请求应携带 `auth-service` 签发的用户 JWT。
2. JWT 至少应包含：

   - 用户主体标识。
   - `token_type=user`。
   - 用户角色声明。
   - 签发时间和过期时间。
3. Agent 应验证用户已经通过认证。

### SEC-02 用户令牌透传

1. Agent 调用 Employee 或 Transaction 时，应透传当前用户的 JWT。
2. Adapter 不得重新定义或修改用户角色。
3. Adapter 不得将无权限用户转换为固定高权限 Agent 身份。
4. 下游返回 `401/403` 时，调用必须失败关闭。

### SEC-03 业务域授权

1. `employee-service` 是 Employee 查询权限的最终执行点。
2. `mq-procedure-service` 是 Transaction 查询权限的最终执行点。
3. 每个业务域应独立定义本域查询接口允许的角色。
4. 业务系统应验证 JWT 有效性、用户类型及角色权限。
5. Agent 和 Adapter 中不得保存业务域角色白名单。
6. 调整某个业务域的允许角色时，不应要求修改 Agent 核心代码。

### SEC-04 角色映射

1. `auth-service` 负责用户与角色的分配及角色声明签发。
2. `common-security` 应统一将 JWT 中的 `role` 声明转换为 Spring Security `GrantedAuthority`。
3. Employee 和 Transaction 应基于转换后的 Authority 执行授权。
4. 不得由各业务服务重复实现不一致的 JWT 字符串解析逻辑。
5. 缺少角色、角色格式错误或角色不满足要求时，应拒绝访问。

### SEC-05 服务身份

1. 第一阶段的查询均基于用户请求，不要求固定 Agent 服务身份。
2. 当前服务令牌机制不作为本期默认查询身份。
3. 如果未来出现定时任务、异步工作流或无用户上下文调用，应另行设计由认证体系管理的服务身份和权限。
4. 即使未来使用服务身份，最终授权仍应由目标业务系统执行，不得转移到 Adapter。

## 8. 扩展性需求

### EXT-01 新增能力

新增查询能力时，应主要通过以下方式完成：

- 新增能力实现。
- 新增 Adapter 模块或 Adapter 实现。
- 新增查询动作配置。
- 在统一能力注册入口完成注册。

不得通过不断向 Agent 核心增加业务域条件分支实现扩展。

### EXT-02 不侵入已有能力

新增能力时：

- 不得修改已有能力的业务实现。
- 不得修改其他业务域 Adapter。
- 允许在稳定注册入口增加必要注册或配置。
- 公共能力接口发生必要变化时，应评估全部实现兼容性。

### EXT-03 Multi-Agent 预留

当前仅预留：

- Agent 编排与具体能力实现之间的边界。
- 统一的能力请求、结果和执行上下文。
- 能力注册与发现入口。

当前不建设 Multi-Agent 运行时、通信协议、注册中心或分布式任务机制。

## 9. 异常处理需求

1. 无法识别可用能力时，应明确提示当前不支持该问题。
2. 参数不合法时，不得调用业务服务。
3. 查询无数据时，应区分“无结果”和“调用失败”。
4. 业务系统返回 `401/403` 时，不得重试为其他身份或绕过权限。
5. 下游超时或不可用时，应返回明确失败信息。
6. 模型不得根据不完整或失败的数据编造业务结果。
7. 一个查询能力失败时，不得自动扩展为未经用户授权的跨域查询。

## 10. 最小日志与可观测性需求

每次能力调用至少应能够识别：

- 请求或调用关联标识。
- 当前能力标识。
- 查询动作标识。
- 目标业务域。
- 调用结果状态。
- 失败类型。
- 调用耗时。

日志不得记录：

- 用户密码。
- 完整 JWT。
- 密钥。
- 不必要的敏感业务数据。

本期不要求建设独立审计平台或复杂链路追踪系统。

## 11. 测试要求

至少覆盖：

1. 知识库查询成功、无结果和失败。
2. 问题改写保持原问题核心语义，改写失败时行为明确。
3. 多知识域只能选择已注册且启用的逻辑知识域，模型不能指定物理索引。
4. 关键词召回、向量召回及组合召回分别可验证。
5. 多路候选能够去重、融合和重排，单路失败与整体无结果能够区分。
6. 答案摘要只使用检索证据，证据不足时明确拒答或说明未找到。
7. Knowledge Adapter 不调用 ES 写入、删除、批量索引或重建接口，不透传模型生成的任意 ES DSL。
8. Employee 查询成功、参数拒绝、无权限和下游失败。
9. Transaction 查询成功、参数拒绝、无权限和下游失败。
10. 允许角色访问成功。
11. 不允许角色返回 `403`。
12. 缺少 JWT 返回 `401`。
13. 缺少或格式错误的角色声明失败关闭。
14. Adapter 正确透传用户 JWT。
15. Adapter 不包含业务角色判断。
16. 未注册或未启用的查询动作不能执行。
17. 非白名单过滤、排序或分页参数被拒绝。
18. 新增模拟能力时，不需要修改已有能力实现。
19. Agent 不直接访问 Employee/Transaction 数据库或 ES。
20. 下游调用失败时 Agent 不生成虚假业务答案。

## 12. 第一阶段验收标准

满足以下条件后，可以认为第一阶段完成：

1. 单体 Agent 可以运行。
2. 用户能够通过自然语言完成包含问题改写、多知识域选择、多路召回与重排、证据化答案摘要的知识查询。
3. 用户能够通过自然语言完成 Employee 域查询。
4. 用户能够通过自然语言完成 Transaction 域查询。
5. 三类能力均通过统一能力注册入口接入。
6. Employee 和 Transaction 均通过对应 Adapter 调用已有业务接口。
7. Agent 和 Adapter 不直接查询业务数据库或业务 ES。
8. 查询动作受到配置和白名单限制。
9. 业务系统能够根据用户角色允许或拒绝查询。
10. Adapter 不实现角色授权。
11. 无权限、无数据、参数错误和下游异常均有明确行为。
12. 新增一个模拟查询能力时，不需要修改已有能力实现。
13. 知识查询只能访问已注册知识域和只读检索接口，不能执行任意索引或 ES DSL。
14. 知识库检索与答案效果已通过一组真实问题完成初步验证。
15. 本期未引入独立 `knowledge-service`、跨业务域聚合、业务写入、工作流或 Multi-Agent 实现。

## 13. 实施阶段与节点

| 阶段 | 主要产出 | 完成节点 |
|---|---|---|
| P0 需求确认 | 本需求说明 | 范围、非范围和权限原则确认 |
| P1 总体架构 | 单体 Agent L0 架构 | 模块、依赖方向和演进边界明确 |
| P2 详细设计 | Agent 核心、知识查询流水线、Adapter、查询动作、权限设计 | 接口、知识域、检索策略边界及角色矩阵明确 |
| P3 能力实现 | 三类查询能力 | 问题改写、多域、多路召回与重排、答案摘要及业务查询单模块测试通过 |
| P4 集成验证 | Agent 到三个目标能力的完整链路 | 权限和异常路径通过 |
| P5 效果验证 | 知识库真实问题验证结果 | 形成初步效果结论 |

不要求复杂交接和审批，但每一阶段进入下一阶段前应确认对应节点已经满足。

## 14. 待确认事项

以下事项不影响进入总体架构设计，但应在真实集成前确定：

1. Employee 查询接口允许的具体角色。
2. Transaction 查询接口允许的具体角色。
3. 两个业务服务现有接口能够覆盖的具体有限查询动作。
