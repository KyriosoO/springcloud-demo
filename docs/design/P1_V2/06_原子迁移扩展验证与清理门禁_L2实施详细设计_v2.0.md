## 3. 文档状态说明

本文处于 **Implemented**。用户已授权代码、测试、配置、运行时契约、依赖和数据库 schema source 的本地实施，P1_V2/P2_V3 原子迁移与清理门禁已闭合并通过全量验证。生产数据库迁移、真实 Provider/索引启用和发布仍需独立授权。

## 4. 背景与目标

P1_V2/01～05 已分别冻结 Java/Runtime 契约、可信执行与 Lifecycle、元数据授权/Context/Result Security、Adapter/Domain Metadata 和 Effective Capability Resource Limits。若按目录或服务独立启用，会形成以下不可接受中间态：

- Java/Python Runtime、fixtures 和 Prompt 存在两个 active generation；
- CHAT-only Java type、Context codec 与 SQL CHECK 不一致；
- Planning Artifact、checkpoint 和 Core 使用不同 canonicalization；
- Definition/Authorization/Core/Provider/Result Security 只迁移部分 resource limit；
- Catalog、availability、Projection 与 Adapter Binding 使用不同静态 bundle；
- auth-service 权限事实与 agent-service 本地允许 fallback 同时生效；
- document rewrite 同时存在 Planning Runtime 与 capability-local Provider 两条路径；
- 旧 Handler/Registry/config/DTO 通过 deprecated facade 继续成为第二事实源。

本文把实现过程定义为一个不可分割的 Activation Candidate：内部允许按依赖顺序形成可编译批次，但任何中间批次都不是可发布/可启用产品形态。最终 Release Unit 必须一次关闭旧路径并通过全部门禁，不建设迁移框架、运行时 feature flag、v1/v2 converter 或双写/双读。

## 5. 设计范围

### 5.1 范围内

- P1_V2/01～05 所有目标结构的依赖顺序、激活边界和完整交付证据。
- Planning Artifact PAI-1 唯一 canonicalizer 的迁移与 checkpoint/Core 一致性门禁。
- CHAT-only Invocation/Context/SQL 的同步切换。
- Capability Definition/Registration、typed resource limits、Domain Metadata/Adapter 和 capability-local port 的纵向切换。
- UserPermissionAuthorityPort 到 auth-service 唯一权威源的最小内部 HTTP 契约和原子 wiring。
- Java -> OpenAPI -> generated Python/fixtures/Prompt、Runtime Route/Plan endpoint 与旧 contract 的一次切换。
- Context/Result/secret/SQL/config 的原子迁移和旧路径删除台账。
- query.preview 与 sample_domain 两类代表性扩展及 Core no-diff 证明。
- 实施授权前置、失败隔离、非生产回退原则、验证命令和退出门禁。

### 5.2 范围外

- 实际修改 Java、Python、SQL、配置、测试或远端环境。
- P2_V3 的 DocumentResourceLimit 字段、索引/ACL/检索/生成业务算法和 Provider HTTP DTO。
- 修改 L0/L1、P1/P2/P2_V2 历史正文或状态。
- Multi-Agent Coordinator、Run/Task/Attempt、ResultRef、Delegation storage、usage ledger 和调度重试。
- 为未投产系统保留兼容 facade、双协议、双表、双配置或可回退到旧运行链的 feature flag。

## 6. 上级文档约束

1. 当前仅实现 CHAT + ConversationScope；future Multi-Agent concrete type 必须等待 Multi-Agent L1。
2. Java 是 Runtime wire contract、执行类型和安全结构的权威源；Python 只接受生成物。
3. Runtime 只负责 Route/Plan，不执行 capability、权限、Adapter 或 capability-local Provider operation。
4. Planning Artifact 使用 P1_V2/02 的逻辑 identity，不使用 JVM reference/object identity。
5. Capability resource limits 只使用 P1_V2/05 的单 Contract typed declaration、source-aware resolver 和同值/收紧证明。
6. Validator、Handler、Adapter/Provider Operation Context 和 Result Security 消费同一 Effective limits view/reference；禁止消费者重算。
7. Profile/Policy/Permission、Canonical Domain Metadata、Registration、availability 和 Provider config 不得互相复制事实。
8. Context 只在 capability 确定后加载；SUCCESS result/Context/Invocation/Turn 在同一 Agent DB 本地事务终结。
9. Caller、Route、Plan、repair、Core、Handler、Adapter、Provider 和下游共享一个 absolute deadline；取消和迟到结果 fail closed。
10. 系统未投产，不保留 v1/v2 兼容层；但破坏性数据清理、公共/跨服务契约、DDL 和生产依赖实施仍须单独授权。

| 不变量 | 强制规则 |
|---|---|
| 一个激活候选 | M1～M6 只构成同一 Activation Candidate；中间批次不得发布、路由流量或标记 Implemented |
| 无运行兼容层 | 不新增 feature flag/facade/converter/双 endpoint/双 Registry/双配置来维持旧链 |

| 入口 CHAT-only | Java permits/factory/codec、SQL CHECK、fixture 和配置同时只接受 CHAT/CONVERSATION |
| 权限唯一权威 | 生产只有 AuthServiceUserPermissionAuthorityAdapter；无 JWT role、本地 allow-all 或缓存允许 fallback |
| 限额同源 | Definition/Profile/Policy/Permission/optional Request 在授权边界求交；实现配置只可成为 operational cap |
| Domain 静动分离 | static Catalog/Registration bundle 与请求级 availability 分离；Projection/Binding 一次原子解析 |
| Runtime 仅规划 | /runtime/v1/route、/runtime/v1/plan 是唯一业务 endpoint；document rewrite 完全迁出 |
| 状态事实唯一 | Invocation 是唯一执行审计状态机；迁移批次状态不进入业务数据库 |

## 9. 总体设计

~~~text
M0 设计与实施授权/影响面预检
  -> M1 Java contract 与 Spring-free leaf SPI candidate
  -> M2 Registration/resource/domain static composition candidate
  -> M3 Authorization/Context/Result Security candidate
  -> M4 Planning/Lifecycle/Core/CHAT vertical chain candidate
  -> M5 Adapter/capability/provider vertical chain candidate
  -> M6 OpenAPI/Python/Runtime/SQL/config/legacy cleanup candidate
  -> M7 full gates + release evidence

M1～M6 = one inactive Activation Candidate
M7 all pass + required authorization = one Release Unit
~~~

每个批次可以在本地分开评审、编译和测试，以缩小定位范围；“批次出口通过”只说明本地候选可继续累积，不授予部署/启用权。任一 G0～G11 门禁失败，整个候选保持未激活并回到产生问题的批次修正，不通过旧路径 fallback。

## 10. 详细功能设计

### 10.1 交付术语与激活边界

| 术语 | 含义 | 明确不代表 |
|---|---|---|
| Work Batch | 本地候选中的依赖有序变更集合 | 可单独部署的版本 |
| Activation Candidate | M1～M6 累积后的唯一新执行链候选 | 与旧链并行运行 |
| Gate Evidence | G0～G11 命令、测试、扫描和授权记录的安全摘要 | 业务运行状态或数据库实体 |
| Release Unit | Gate 全过后一次部署/启用的 Java/Python/SQL/config 闭合集 | 多阶段灰度双协议 |

代码评审可以按模块拆 diff，但最终不得只合入/发布其中一段。若受仓库流程限制必须拆多个 commit，它们仍属于同一未激活分支和一个 Release Unit；本文不授权 commit/push/PR。

### 10.2 M0 影响面、数据与授权预检

实施前必须形成只读预检清单：

1. 固定实施基线 commit、P1_V2/P2_V3 目标文档版本和全部当前调用者。
2. 列出将改变的公共/跨服务 DTO、Runtime wire contract、auth internal API、SQL DDL、配置 key、secret reference 和生产依赖。
3. 统计 Invocation/Context 表中非 CHAT、RUN/TASK、未知 codec/version 数据；只执行只读 count/sample-safe-digest，不输出 payload。
4. 验证 P2_V3/02～06 已通过，Document limits、ACL/evidence、candidate 与 rewrite 替代 Port/DTO/client 可在同一候选完成。
5. 验证工作树现有用户改动已识别，实施不得覆盖无关 diff。
6. 对公共/跨服务契约、DDL、非 CHAT 数据清理、新生产依赖和发布动作分别取得用户明确授权。

任一授权缺失或发现非 CHAT 数据，M0 停止。不得把数据静默转为 ConversationScope、直接删除、创建兼容 reader，或用“系统未投产”绕过用户授权。

### 10.3 PAI-1 canonicalizer 唯一迁移

PAI-1 字段与语义由 P1_V2/02 唯一定义。本文只冻结迁移动作：PlanningArtifactCanonicalizer.identify(InvocationHandle, PlanningArtifactComponents) 是唯一生产入口，Builder、ExecutionCommand 和 Core 不允许调用其他 serializer/digest helper。

PlanningArtifactComponents 的 canonical input 必须完整覆盖：

- format marker PAI-1；
- invocationId、requestCorrelationId；
- capabilityId、optional domain、planKind；
- registration stable identity；
- Raw Plan canonical contract digest；
- Authorization Snapshot safe reference（其内部绑定同一 Effective limits reference）；
- 按稳定业务 key 排序的 Context Snapshot safe references；
- Route/Plan operation metadata safe digest；
- absolute deadline。

禁止把 Profile/Policy/Permission 正文、Raw Plan payload、Context payload、provider response、capturedAt 等非语义时间、Java class name、对象地址或 toString() 放入 canonical form。无序 Map/Set 按稳定 key 排序；只有 P1_V2/02 强类型字段明确声明为有序语义的 List 才保留顺序，其他集合按稳定业务 key 规范化。字段名、null/empty、UTF-8、enum wire value 和 epoch millis 语义固定。SHA-256 输出 lowercase hex。

ExecutablePlanningResult 先形成 identity-free components，再由 canonicalizer 构造 PlanningArtifactIdentity。ExecutionCommand 和 Core 从同一强类型 components 重算并常量时间比较。PlanningCheckpoint/checkpoint_json 使用 P1_V2/02 的 planningArtifactBindingDigest，checkpoint_hash 覆盖该值；不新增第二个 artifactBindingDigest 命名或独立恢复协议。系统当前不恢复执行，未知/不一致 identity 只用于拒绝和审计。

### 10.4 Capability resource declaration 与同源切换

本文删除原 ResourceLimitDeclaration 近似类型。CapabilityDefinition 必须直接声明 P1_V2/05 的：

~~~java
CapabilityResourceLimitDeclaration<T extends CapabilityResourceLimit>(
    ContractRef contractRef,
    Class<T> limitType,
    T intrinsicUpperBound,
    Set<ResourceLimitDimension> applicableDimensions)
~~~

原子闭合项：

1. CapabilityResourceLimitRegistry 与 Capability Registration 作为同一 composition bundle 构建和发布。
2. 每个 Registration 绑定且只绑定一个 declaration；缺失、重复、unknown ContractRef、type/dimension mismatch 启动失败。
3. Profile/Policy/Permission 各形成一个有 evidence 的 typed contribution；Request 只可选收紧。
4. Authorization Planning freeze 完整 Effective value；Execution recheck 使用同一 contract 生成同值或可证明更严格值。
5. ExecutionValidationContext、ExecutionContext/CapabilityOperationContext、Adapter/Provider 和 ResultSecurityPort 使用同一 view/reference。
6. AvailableCapability、Domain Projection、AgentProperties 和 Projector 不保存/重算 page/rows/bytes/evidence/generation 散预算。
7. Provider connect/read timeout、response bytes 和 bulkhead 只作为 operational cap；不能直接成为 resolver source。

### 10.5 UserPermissionAuthority 内部 HTTP 契约

UserPermissionAuthorityPort.resolveCurrent(ExecutionSubjectRef, Instant absoluteDeadline) 保持 P1_V2/03 的最小内部 SPI。生产唯一实现为 AuthServiceUserPermissionAuthorityAdapter，调用：

| 项 | 契约 |
|---|---|
| Method/Path | POST /internal/agent/permissions/resolve |
| Content-Type | application/json |
| Authentication | Authorization: Bearer service-token；service identity=agent-service，scope=agent.permission.resolve |
| User credential | 不转发用户 JWT/cookie/session/role claim |
| Retry/cache | 不自动重试；P1_V2 不缓存成功允许结果 |
| Timeout | connect stage cap；read=min(configuredReadTimeout, remaining absolute deadline)；调用前后检查 deadline |
| Response cap | 默认最大 64 KiB，超出按 INVALID_RESPONSE 拒绝 |

Request 只包含：

| 字段 | 类型 | 约束 |
|---|---|---|
| requestId | String | agent-service 生成的安全关联 ID |
| subject | {type,id} | 当前仅 USER；id 与 ExecutionSubjectRef 精确一致 |
| requestedAt | Instant | adapter Clock 生成 |
| deadline | Instant | 同一 Invocation absolute deadline |

不得发送固定配置伪造的 agentId/profileId/scopeType/scopeId，也不得发送 requested capability/domain 让权限源误把调用方请求当授权事实。Profile、Policy、ConversationScope 和 capability selection 继续由 agent-service 的授权边界独立收紧。

Response 与 agent-service UserPermission 一一对应：

| 字段 | 类型 | 规则 |
|---|---|---|
| subject | {type,id} | 必须与 request 精确一致 |
| evidenceId / version | String | 非空；projection 或授权规则变化时相应变化 |
| allowedCapabilityIds / allowedDomains | Set<String> | 非 null；空表示无权限 |
| filterableFields / displayableFields | Map<domain,Set<field>> | canonical id；非 null |
| allowedOperators | Map<domain.field,Set<AgentOperator wire value>> | unknown enum 拒绝 |
| allowedFunctions | Map<domain.field,Set<function id>> | 由 canonical metadata 再闭合校验 |
| readableContextTypes / writableContextTypes | Set<String> | ContractRef/context type allowlist 再校验 |
| attributes | Map<String,String> | 仅安全附加事实；不得作为散 budget/JWT/role expression 或未知授权扩展点 |
| resolvedAt | Instant | 不晚于响应生成时间，不晚于 adapter 接收时间的容忍窗口 |

所有集合/Map 必须非 null，agent-service 仍执行 subject、enum、canonical id、大小/深度、version/evidence 和 deadline 校验。Permission resource contribution 由 agent-service Authorization/metadata 内的 contract-specific adapter 基于该权限证据形成；auth HTTP DTO 不复制 capability limit subtype。

错误契约：

| auth-service code | HTTP | agent-service failure | 语义 |
|---|---:|---|---|
| AGENT_PERMISSION_INVALID_REQUEST | 400 | INVALID_RESPONSE | 本地请求/契约缺陷，fail closed 并告警 |
| 无可信业务 code（security filter 拒绝） | 401/403 | UNAVAILABLE | 不解析/信任 body；作为服务身份配置事故审计，不向客户端暴露细节 |
| AGENT_PERMISSION_SUBJECT_NOT_FOUND | 404 | SUBJECT_NOT_FOUND | 当前主体无权威记录 |
| AGENT_PERMISSION_UNAVAILABLE | 503 | UNAVAILABLE | 权威源不可用 |
| AGENT_PERMISSION_DEADLINE_EXCEEDED | 504 | DEADLINE_EXCEEDED | absolute deadline 已到期 |
| AGENT_PERMISSION_INTERNAL_ERROR | 500 | UNAVAILABLE | 安全 diagnosticId，禁止原始异常/响应体 |

若 client stage timeout 发生时 absolute deadline 尚未到期，映射 UNAVAILABLE；只有 deadline 已到期才映射 DEADLINE_EXCEEDED。auth-service 是 HTTP contract owner，agent-service 使用私有 client DTO；双方以同一正/负 JSON fixture 和 contract test 闭合，不新增远程 Registry 或第三个权限 API 模块。

### 10.6 M0～M7 原子实施批次

| 批次 | 主要动作 | 同批闭合项 | 批次出口（不等于可发布） |
|---:|---|---|---|
| M0 | 文档/调用者/数据/授权预检 | P2 provider 前置、公开契约/DDL/依赖/清理授权 | G0 可证明 |
| M1 | Java source contract 与 Spring-free leaf SPI | agent-api ContractRef/Route/Plan/Error/Result；agent-adapter-api operation/role/typed Adapter SPI；auth permission wire DTO | leaf modules 编译，contract candidate 可生成 |
| M2 | 静态 composition 基础 | Definition/Registration/Registry/typed bridge；resource Contract Registry；Domain static Catalog/Registration builder/store；consumer/coverage gate | generic type、builder 和 gate 测试闭合；不发布未完成 bundle |
| M3 | Authorization/Context/Result Security | Profile/Policy/Permission/currentness；resource resolver/freeze/recheck；Context codec/crypto/CAS；Result projector/Mask；secret purpose 隔离 | 安全边界测试通过 |

M1～M6 必须存在于同一最终候选中。不得把 M1 新类型作为未使用“预留”长期合入，也不得先上线 auth endpoint/SQL 后让旧 agent-service 继续按另一语义运行。确需多个服务分步部署时，必须另行 ADR 定义无双协议的部署顺序和兼容窗口；当前设计默认同一非生产环境整体重建/部署。

### 10.7 Capability v2 唯一调用链

~~~text
AgentChatController / Entry Adapter
  -> StartTxService: Turn + Invocation(PROCESSING) committed
  -> PlanningService
       -> AuthorizationPlanningPort.capture/assertCurrent
       -> CapabilityCatalog.available
       -> Runtime Route
       -> Resolved Registration
       -> capability Context + Domain Plan Schema
       -> Authorization freeze including Effective limits
       -> Runtime Plan
       -> ExecutablePlanningResult + PAI-1
  -> ExecutionLifecycleService checkpoint committed
  -> ExecutionCore
       -> identity/currentness/Context/Domain Binding/limits recheck
       -> Registration-bound Validator
       -> Registration-bound Handler
       -> Adapter and/or capability-local Provider
       -> output validation + Result Security + Context approval
  -> FinalizationTxService
       -> result + Context + Invocation + Turn one local transaction
  -> AgentChatResponseAssembler from FinalizedInvocationResult
~~~

Clarification/Planning failure/cancellation 在 checkpoint/Core 之前由 Lifecycle 安全终结；Execution failure 由 Core 返回 typed outcome 后终结。任何 commit-unknown 只权威重读，不重跑 Planning/Handler/Adapter/Provider，不补写 SUCCESS。

### 10.8 CHAT-only Java/codec/SQL 切换

同一 M4/M6 候选必须完成：

- 删除 RunScope、TaskInvocationOrigin 和 InvocationType.TASK；
- InvocationScope permits ConversationScope；
- InvocationOrigin permits ChatInvocationOrigin；
- InvocationHandle 只暴露当前 forChat(...) concrete factory；
- ContextBindingSupport 只 encode/decode CONVERSATION，RUN/unknown fail closed；
- Invocation SQL 只允许 origin_type=CHAT、scope_type=CONVERSATION，不新增 run/task/attempt 列；
- main source、配置和生产 fixture 无可构造 TASK/Run shape；
- 测试可保留“拒绝 Run/Task”名称和字符串，但不得保留可成功构造的 future subtype。

数据库预检发现非 CHAT 数据时停止实施并请求数据处理授权；禁止静默转换或删除。

### 10.9 Contract generation 与 Runtime 边界切换

Java source contract 修改后按 P1_V2/01 固定链生成 OpenAPI candidate、正负 fixtures 和 generated_models.py。models.py 只允许无语义 import facade；不得补字段、改 enum、放宽 extra 或保留 v1 model。

Runtime 最终业务 endpoint allowlist 只有：

- POST /runtime/v1/route；
- POST /runtime/v1/plan。

健康/治理 endpoint 单独 allowlist，不属于业务 operation。/runtime/v1/document/rewrite、app/core/document_rewrite.py 及其 DTO/Prompt/测试必须在 P2 capability-local rewrite client 可用的同一 M5/M6 候选删除。旧 agent-api.response.RuntimeErrorResponse、单 operation plan DTO、手工 Python parallel model 和 candidate patch 路径同时删除。

### 10.10 Domain Metadata 与 Adapter 切换

M2 构建唯一 DomainMetadataStaticBundle：canonical Catalog、static Adapter Registration 和 role→port type 映射全量校验后原子发布。M4/M5 的请求级链只通过 DomainMetadataPort 获得 availability/Route Projection/Plan Schema，并通过一次 resolveExecution 原子获得 Execution Projection + Adapter Binding。

同步删除：

- DomainCatalogView 和 Validator 对 metadata.domain.internal 的依赖；
- Registration 中 roles/enabled/portType/catalogVersion 重复字段；
- Domain properties/projection 的 page/result 散预算；
- Adapter 自报 fields/operators/functions/capabilities；
- Prompt 中生产 domain/field 示例和 Default bootstrap 专用事实遍历；
- Handler 二次按 domain/role 查找 Adapter。

employee/transaction 下游保留自身独立字段/排序白名单作为业务边界防御；通过 coverage/contract test 证明它是 Agent canonical mapping 的可执行子集，不删除为“重复事实”。

### 10.11 Capability-local Provider 与 P2 前置

P1_V2/05 的 operation SPI 在 M1 进入 agent-adapter-api，具体 resolver/Effective 实现在 M3，Document typed request/outcome/client 在 M5 由 P2_V3/02～06 落实。每个 operation 必须：

1. 从同一 ExecutionContext 创建 operationId/deadline/cancellation/limits view；
2. 最多一次可观测 outbound attempt，自动 retry 全关闭；
3. pre/post check deadline/cancellation/binding；
4. stage timeout、absolute deadline、late result 和 security rejection 使用不同 typed failure；
5. Provider candidate 不写 Context/日志/响应，必须经 Handler validator 和最终 Result Security；
6. rewrite client 不依赖 AgentRuntimeClient、Planning DTO、Runtime Prompt 或 repair。

若 P2 provider 设计/实现未就绪，允许继续评审或本地完成 M0～M4 的非激活候选；M5/M6/G8 不得通过，P1_V2 代码不得标记 Implemented。

### 10.14 失败隔离与回退原则

当前系统未投产且明确不保留双协议，回退单位只能是完整候选：

- M1～M6 期间失败：候选保持未激活，在同一工作分支修正；不启用旧/新混合链。
- M7 失败：不得发布、不得标记 Implemented、不得删除外部环境数据；保留失败证据和未验证项。
- 非生产环境首次整体部署失败：回到部署前完整应用/配置/数据库快照，或在获授权后从目标 schema 重建；不得只回退一个服务/一张表。
- DDL/data preflight 失败：停止并请求用户决定；本文不授权自动清理、转换或 destructive rollback。
- Runtime/Lifecycle commit unknown：按 P1_V2/02 权威重读并服从已提交状态，不通过重新调用 Provider/Handler“回退”。
- 发布后若未来需要兼容窗口或独立服务分步回退，必须另行 ADR；当前文档不以未设计的生产场景引入 feature flag。

### 10.15 P2_V3 准入与实施边界

P1_V2 文档评审通过可作为 P2_V3 评审输入；P2_V3 不得反向修改 PAI-1、Invocation/Lifecycle、Authorization Snapshot、Domain Binding、operation SPI 或 Result Security seam。只有以下条件同时满足，Document 相关 M5/M6 才可实施：

- P2_V3/02 的 DocumentResourceLimit 与 P1_V2/05 Contract 完整闭合；
- P2_V3/03 的 ACL/evidence/currentness 不绕过 P1_V2/03；
- P2_V3/04 的 retrieval 使用 P1_V2/04 Adapter Binding 和同一 operation context；
- P2_V3/05 的 generated candidate 实现 P1_V2/05 security binding；
- P2_V3/06 的 rewrite/embedding/rerank/generation typed client 替代 Runtime rewrite；
- P2_V3/07 不通过 retry/缓存/降级放宽 P1 门禁。

### 10.17 Multi-Agent 演进边界

当前迁移只保留中立的 subject/owner/scope/ref/deadline/Invocation/Planning/Execution 接口，不创建 RunScope、Task owner、Delegation repository、ResultRef、Task budget source 或调度状态。future Multi-Agent L1 可以增加新的 concrete scope/origin、Task State Boundary 和 source-aware resource narrowing；不得要求保留当前旧 TASK 空壳，也不得改变本文冻结的单 Agent 执行内核和 operation consumer seam。

## 12. 数据设计

本文不复制 P1_V2/02、03 的完整 DDL，只冻结同一 Release Unit 的数据边界：

| 数据对象 | 权威文档 | 原子切换要求 |
|---|---|---|
| agent_turn | P1_V2/02 | Start/finalization 与 Invocation 同 Agent DB 事务；CHAT shape |
| agent_invocation_record | P1_V2/02 | PROCESSING/终态、checkpoint sequence/hash、PAI binding、CAS、CHAT/CONVERSATION CHECK |
| agent_invocation_result | P1_V2/02 | 只保存 secured SUCCESS；CLARIFY/FAILED/CANCELLED 无结果行 |
| Capability Context | P1_V2/03 | Owner+ConversationScope+type/version、AEAD/AAD/key、TTL、CAS、retirement/cleanup |
| Effective limits/operation candidate | P1_V2/05 | Invocation 内 immutable；DB/audit 只保存 safe reference/digest/metadata 摘要 |
| Permission evidence | P1_V2/03/本文 10.5 | 保存 evidenceId/version/safe digest；不保存权限正文或 auth response |

数据 preflight 只查询 count、type/version 分布和安全主键摘要。非 CHAT/unknown schema/unknown key 数据均阻断，处理方式必须由用户授权。不得建立临时双写列或把完整 Raw Plan/Permission/Provider payload 放入 checkpoint_json。

## 13. 状态流转设计

迁移不增加业务状态机。Invocation 仍只有 P1_V2/02 的 PROCESSING -> COMPLETED|FAILED|CANCELLED。

文档/实施状态独立治理：

~~~text
In Review --全套评审+用户批准--> Approved
Approved --实施授权+M0通过--> Implementing
Implementing --M1～M6 candidate complete--> Candidate Ready
Candidate Ready --M7/G0～G11全过--> Implemented
~~~

Candidate Ready 是交付描述，不写数据库、不新增 enum/表。任一 Gate 未通过仍是 Implementing，不得提前把文档或代码标记 Implemented。

## 14. 幂等、事务与一致性设计

- PAI-1、metadata digest、resource digest、Context binding digest 对同一逻辑输入确定性相同。
- Java/OpenAPI/Python/generated fixture 使用同一 source candidate 原子生成，不手改修补。
- Start、checkpoint、SUCCESS finalization 和 failure/cancel finalization 遵守 P1_V2/02 的本地事务/CAS；commit unknown 权威重读。
- Domain static bundle 原子发布；Execution Projection/Binding 使用同一次 bundle/availability evidence。
- Permission Planning capture 与 Execution recheck 每次读取当前权威源；无成功缓存 fallback。
- operationId 在 Invocation 内唯一但不是业务幂等键；网络异常不自动重放 Provider。
- SQL/Java enum/codec/factory/config 在同一 Release Unit 切换，不双写 CHAT/TASK 或新旧 digest。

## 15. 权限、风控与审计设计

- Gate/启动错误只输出 capabilityId、ContractRef、stage、reasonCode、diagnosticId 和 safe digest prefix；不输出 permission/limit/config/secret 正文。
- auth 请求不携带用户 JWT、角色表达式、Profile/Policy、Conversation 内容或 requested capability 作为授权事实。
- service token 只由 ServiceTokenProvider/common-security 提供，不写配置值、日志、checkpoint 或 response。
- PAI canonical form 不含 Raw Plan/Context/Prompt/Provider response；digest 不替代 Execution currentness。
- Provider credential 只在 client boundary 注入，operation context/outcome 不携带 credential/endpoint。
- destructive data cleanup、DDL、公共/跨服务 contract、生产依赖和发布均以 M0 授权记录为前置。

## 16. 性能与容量设计

- PAI-1 在生成、Command/Core 校验处对有界 safe components 计算；不远程调用、不跨 Invocation 缓存。
- Registry/resource/domain static closure 只在 build/startup/reload candidate 执行。
- Permission response 默认 <=64 KiB；集合/Map 数量和字符串长度必须有 contract 上限，超限 INVALID_RESPONSE。
- data preflight 使用索引列 count/group 与有界 sample-safe-digest，禁止全表 payload 扫描和日志输出。
- Provider/Adapter 队列等待计入 absolute deadline；bulkhead/response cap 有界，无 retry buffer/late result accumulation。
- Gate 静态扫描限定生产路径并使用 allowlist，避免扫描历史文档造成假阳性。

## 17. 兼容性与扩展性设计

当前系统未投产，因此最终候选不保留旧 Runtime endpoint、DTO、Handler、TASK seam、Context codec、散预算或配置兼容层。兼容性只允许：

- Java source contract 的显式版本与生成物一致性；
- PAI/checkpoint/Context schema 的显式版本拒绝；
- transaction 等已存在外部业务 API 在未获授权时保持原字段语义；
- 历史设计文档作为 provenance 只读保留。

future Multi-Agent、Provider retry、缓存、远程 Adapter discovery、拆分数据库或跨进程事务均须独立 L1/ADR，不通过当前空字段或 facade 预留。

## 21. 风险与待确认事项

| 风险 | 触发场景 | 影响 | 处理 | 是否阻塞 |
|---|---|---|---|---:|

| 公共/跨服务契约与 DDL 授权 | 实施改变 Runtime/auth/business DTO 或 schema | 调用者/数据受影响 | M0 清点并逐项取得用户授权 | 阻塞实施 |
| 当前 auth request 过度字段 | adapter 仍用固定 profile/scope config | 权限投影与当前 Invocation 不一致 | 按 10.5 最小 request 原子改双端和 fixture | 阻塞 G5 |

| 非 CHAT/unknown schema 数据 | preflight count 非零 | 直接新 schema/codec 会拒绝读取 | 停止并请求清理/保留决定，不自动操作 | 阻塞实施 |
| 原子范围大 | 任一服务/SQL/config 半切 | 无法编译、越权或双事实源 | 内部批次定位、一个 Activation Candidate、全 Gate 后激活 | 不阻塞设计 |

| 非生产回退未演练 | 整体部署失败只回退一部分 | schema/app 不一致 | P2_V3/07 演练完整 artifact/config/schema snapshot 或重建 | 阻塞发布 |
