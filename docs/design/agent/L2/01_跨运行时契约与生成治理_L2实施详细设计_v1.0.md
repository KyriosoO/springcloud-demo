## 3. 背景、目标与范围

### 3.1 背景与问题

P0 已把旧 `agent-*` 资产迁入 `*_alpha` 并建立新的同名空骨架。当前目标 `agent-api` 没有 Java 契约源码或 OpenAPI，`agent-runtime` 没有契约模型、生成器和服务端点，`agent-service` 没有 Runtime 客户端或兼容性门禁。旧 alpha 中存在 Java DTO、OpenAPI、Python 生成脚本和生成模型，但它们属于历史实现，不能复制为目标基线。

当前需要解决的设计根因不是“缺少一批 DTO”，而是跨语言契约尚无唯一编辑源、派生产物边界、确定性生成规则和不兼容实例隔离机制。若直接由 Java、Python 分别手写模型，会形成双重权威；若把 alpha 文件恢复为活动源码，会违反 P0 隔离结果。

### 3.2 目标与验收行为

| 需求编号 | 目标或可观察行为 | 验收标准 | 来源 |
|---|---|---|---|
| REQ-01-001 | 建立唯一跨运行时契约权威 | 只有新 `agent-api` 内一个受版本控制的 OpenAPI 根文件允许人工语义修改；Java/Python 派生产物均能追溯到它 | L0 `AD-03`、`DEC-02`；Agent L1 `APP-DEC-03` |
| REQ-01-002 | 双端生成可复现且不可手工漂移 | 相同源、生成器版本和参数连续生成两次得到字节一致产物；已提交 Python 模型、制品元数据和 lock 与临时重生成结果一致 | L0 契约质量门禁；总览 `DR-003` |
| REQ-01-003 | 不兼容实例失败关闭 | Java 只向 `contractFingerprint` 精确匹配且具备所需 capability 的 Runtime 实例发请求；无兼容实例时返回稳定错误并不调用模型 | L0 `AD-19`、`DEC-12` |
| REQ-01-004 | 版本和兼容变更可审计、可回滚 | 变更按 SemVer 分类，兼容矩阵、源哈希、生成器版本和产物哈希进入锁文件；蓝绿制品可按完整配对回切 | Agent L1 第 7.1、13 节 |
| REQ-01-005 | 契约错误具有稳定的调用方语义 | 结构、版本、能力、deadline 和内部故障分别使用稳定错误码；可获得时携带安全关联标识；异常文本不成为契约，Runtime 不决定 Java 是否重试 | L0 `AD-11`、`AD-16`；Agent L1 第 7.5、9.3、10.3 节 |
| REQ-01-006 | 后续专题能安全贡献业务 Schema | 生命周期、能力、DOCUMENT、Tool 安全专题只能通过 OpenAPI 源和契约变更清单贡献字段；01 不替代其业务语义所有权 | 总览 `DR-004`、`DR-005`、`DR-009` |

### 3.3 范围内

- `agent-api` 中 OpenAPI 根文件、契约锁文件、Java 生成配置和契约发布边界。
- `agent-runtime` 中 Python 模型生成、来源标记、漂移检查和生成依赖隔离。
- 公共契约元数据、统一错误封套、readiness 响应以及能力 Schema 的贡献规则。
- `contractVersion`、`contractFingerprint`、`capabilities` 的计算、比较和失败关闭。
- 契约变更分类、混合版本隔离、蓝绿发布和整组回滚。
- 生成、fixture、兼容和架构边界测试。

### 3.4 范围外

- QUERY、AGGREGATE、DOCUMENT 的业务字段、Prompt、规划算法、检索参数和结果质量公式。
- 执行状态机、数据库事务、重试次数、取消栅栏、回调和持久化 Schema。
- Runtime→Tool 凭据格式、轮换、撤销、防重放和权限判定算法。
- `employee-service`、`mq-procedure-service`、`es-query-service` 或外部模型提供方契约。
- Runtime Web 框架、服务发现、负载均衡器、生产端口、SLO、容量和 HA 选型。
- 生产发布、Runtime 服务监听、服务发现接入和流量切换。

### 3.5 非目标

- 不把 OpenAPI 做成运行时动态配置或第二套服务注册中心。
- 不为了未来 multi-agent、写操作或多语料库预建字段和抽象。
- 不复制 `agent-api_alpha` DTO、fixtures、OpenAPI 或 `agent-runtime_alpha` 生成脚本。
- 不用宽松反序列化、忽略未知 discriminator 或默认值掩盖契约不一致。

## 6. 当前实现基线与最小变更方案

### 6.1 当前实现事实

| 证据 | 已确认事实 | 设计含义 |
|---|---|---|
| `agent-api/pom.xml` | 目标模块只有 POM，无 `src` 契约文件；继承 Java 25/Spring Boot 3.5.10 基线 | 可从唯一 OpenAPI 源建立，不需要兼容目标模块旧源码 |
| `agent-runtime/pyproject.toml` | Python 3.12，生产依赖为空 | 生成工具和 Pydantic 依赖均是建议新增，不能宣称已存在 |
| `agent-runtime/src/agent_runtime/__main__.py` | 仅空闲进程，不监听端口 | 本文不直接启用 Runtime 服务，不改变 P0 空骨架事实 |
| `agent-service` | 只有启动类、隔离配置和空服务测试 | Runtime 客户端、兼容选择器和 readiness 聚合均不存在 |
| `.github/workflows/agent-contract.yml` | 当前只校验目标骨架和 alpha 非活动边界 | 后续需在原 workflow 内增加契约生成/漂移 job，避免平行 CI 权威 |
| alpha/P1_V2 证据 | 证明 Java→OpenAPI→Python 生成和 drift 检查在仓库工具链上可行 | 仅复用经验；目标源文件、类型和脚本重新设计，不复制历史实现 |

### 6.2 当前问题与根因

| 问题 | 直接原因 | 设计根因 | 不处理的影响 |
|---|---|---|---|
| Java/Python 无目标契约 | P0 只创建空骨架 | 尚未确定唯一编辑源与派生方向 | 双端手写或从 alpha 恢复，破坏权威链 |
| 无版本/指纹门禁 | Runtime 尚无协议元数据 | 未冻结比较算法和失败语义 | 混合制品可能接流量并产生静默错配 |
| 无确定性生成 | 目标生成脚本不存在 | 未固定工具版本、参数、产物和漂移检查 | 本地/CI 结果不同或生成物被手改 |
| 能力字段输入尚未齐全 | 后续能力 L2 未完成 | 01 与业务专题所有权需分离 | 01 若自行定义会越权并增加返工 |

### 6.3 最小变更与分阶段方案

| 阶段 | 变更项 | 必要性 | 复用内容 | 不采用方案及原因 |
|---|---|---|---|---|
| M1 | 建立唯一 OpenAPI 根、公共元数据/错误/readiness、锁文件、双端生成和漂移门禁 | 先解决契约治理根因，为后续专题提供稳定入口 | 复用当前 Maven/Python/CI 运行环境，不复用 alpha 源码 | 不采用 Java/Python 双手写；会形成双权威 |
| M1 | 建立 Java 精确指纹兼容选择器的接口和负向测试 | 没有失败关闭就不能安全连接 Runtime | 复用 `agent-service` 目标骨架 | 不采用仅比较版本号；同版本内容仍可能漂移 |
| M2 | 后续专题按贡献协议增加 Route/Plan/DOCUMENT/Tool 业务 Schema | 业务字段必须由真实所有者提供 | 复用 M1 根文件和生成链 | 不在 01 预建业务字段；避免越权和猜测 |
| M3 | Runtime/Tool 服务端实现及蓝绿接流量 | 需要生命周期、安全和部署专题共同关闭 | 复用已生成模型和兼容门禁 | 不由本文直接启用服务；当前没有实现授权和生产门禁 |

M1 是本文独立评审通过后可申请实施的最小闭环。M2、M3 必须分别具备关联 L2 和代码授权；M1 完成不代表 Runtime 业务可用。

## 7. 职责、分层与依赖设计

### 7.1 责任分解

| 组件 | 状态 | 唯一职责 | 明确不负责 | 输入/输出 |
|---|---|---|---|---|
| OpenAPI 根文件 | 建议新增 | 跨运行时 wire Schema 唯一人工编辑源 | Java/Python 业务实现和运行配置 | OpenAPI 3.1 JSON |
| Contract Artifact Orchestrator | 建议新增 | 以 check/update 模式编排规范化、双端生成、制品元数据、lock 和确定性比较 | 判断业务兼容性、自动安装依赖或批准发布 | OpenAPI + fixtures + 固定工具链 → generated/metadata/lock |
| Java Codegen | 建议新增 | 从同一 OpenAPI 生成 Java wire types | 持久模型、业务校验和服务编排 | OpenAPI → generated Java |
| Python Codegen | 建议新增 | 从同一 OpenAPI 生成 Python Pydantic v2 models | Prompt、图节点和语义补丁 | OpenAPI → generated Python |
| Drift Checker | 建议新增 | 由 Contract Artifact Orchestrator 的 check 模式在两个临时目录生成并比较源、lock、元数据和产物 | 自动改写工作区或降低校验 | 仓库状态 → 非零/零退出码 |
| Runtime Contract Metadata Provider | 建议新增 | 返回当前 version/fingerprint/capabilities 和契约自检状态 | 服务发现、依赖健康和流量策略 | build metadata → contract-readiness body |
| Java Runtime Compatibility Gate | 建议新增 | 对候选 Runtime 做精确兼容判断 | 重试、状态迁移或模型选择 | expected + actual metadata → allow/reject |
| Java Runtime Contract Payload Parser | 建议新增 | 在 generated model 绑定前按打包的 OpenAPI 3.1 Schema 校验原始 JSON，并在绑定后执行 Bean Validation | 兼容选择、HTTP 调用、重试或业务校验 | raw JSON + 固定 Schema 名 → generated model 或 `CONTRACT_PAYLOAD_INVALID` |
| Capability Contract Contributor | 待关联专题批准 | 提交业务 Schema、错误、fixture 和兼容分类 | 修改生成器方向或绕过 OpenAPI | 专题设计 → OpenAPI change set |

### 7.2 依赖方向与禁止路径

```text
approved L2 semantics
        ↓
agent-api OpenAPI root → contract lock
        ├──────────────→ generated Java types + packaged OpenAPI → agent-service strict parser → compatibility gate
        └──────────────→ generated Python models → agent-runtime
```

| 调用方 | 被调用方/稳定契约 | 允许原因 | 禁止绕过路径 | 失败语义 |
|---|---|---|---|---|
| Java/Python 生成器 | `agent-api` OpenAPI 根 | 唯一生成输入 | 读取 alpha、另建平行 Schema | `CONTRACT_SOURCE_INVALID` |
| `agent-service` | generated Java types + readiness | Java 保持调用与兼容权威 | 使用 Python 内部模型或忽略 fingerprint | `RUNTIME_CONTRACT_INCOMPATIBLE` |
| `agent-runtime` | generated Python models | Python 严格解析 Java 契约 | 手写同义模型、`extra=allow` | `CONTRACT_PAYLOAD_INVALID` |
| 后续能力专题 | OpenAPI 贡献协议 | 业务所有者提供字段语义 | 直接修改 generated 文件 | `CONTRACT_CHANGE_UNGOVERNED` |
| `agent-service` 严格解析器 | packaged OpenAPI + generated Java types | 原始 JSON Schema 语义不能由 mutable generated POJO 单独保证 | 先绑定再补字段、手写同义 DTO 或只依赖 Jackson `required=true` | `CONTRACT_PAYLOAD_INVALID` |

禁止目标模块依赖任何 `*_alpha` 包、路径、生成物或运行服务。生成脚本只可读取新 `agent-api` 根文件；CI 必须通过活动边界检查证明该依赖方向。

### 7.3 内聚与耦合判断

OpenAPI、锁文件、生成配置和兼容规则共同保护“跨运行时契约一致”这一单一原因，因此归 01 治理；业务 Schema 的语义仍归对应能力 L2。`agent-service` 只依赖 `agent-api` 中打包的 OpenAPI、generated types 和 lock，由严格解析器保护跨运行时不可信输入边界；`agent-runtime` 只依赖生成模型，二者不引用对方内部包。严格解析器不是通用 Contract Manager，也不动态改变 Schema：它只编译随制品发布的固定 Schema，并在调用模型、Tool 或兼容门禁前失败关闭。

## 8. 详细功能与核心流程设计

### 8.1 唯一源、锁文件与指纹

#### 8.1.1 设计规则

| 规则编号 | 规则 | 责任主体 | 触发条件 | 输出/状态效果 |
|---|---|---|---|---|
| DR-01-001 | 唯一人工编辑源固定为建议新增路径 `agent-api/src/main/resources/openapi/agent-runtime-openapi.json`；不得存在第二份活动 Runtime/Tool OpenAPI | `agent-api` | 新建或修改跨运行时契约 | 单一 OpenAPI 3.1 根 |
| DR-01-002 | Java 与 Python wire types 必须从 DR-01-001 的同一文件生成；generated 路径禁止语义手改 | 双端生成链 | 构建或契约变更 | 可追溯派生产物 |
| DR-01-003 | 源、工具坐标/版本和固定语义参数必须连续生成两次字节一致；写入采用同目录临时文件后原子替换 | Contract Artifact Orchestrator | 本地更新或 CI | 可复现结果，否则非零失败 |
| DR-01-004 | `contractVersion` 使用 SemVer；`contractFingerprint` 为规范化 OpenAPI 文件完整 SHA-256，格式 `sha256:<64 lowercase hex>` | Lock Generator | 每次契约生成 | 版本/指纹锁定 |

#### 8.1.2 规范化与锁文件

OpenAPI 源必须是 UTF-8、无 BOM、LF、对象键按字典序稳定输出并以一个换行结束。指纹对该规范化后的完整字节计算；描述、示例或空白的有效变更也会改变指纹，必须至少提升 patch 版本。保守地产生新指纹优先于忽略可能影响生成器的差异。

建议新增 `agent-api/src/main/resources/openapi/agent-runtime-contract.lock.json`，字段固定如下：

| 字段 | 类型 | 规则 |
|---|---|---|
| `lockFormatVersion` | integer | M1 固定为 `1`；未知值必须失败，不得按最接近格式读取 |
| `contractVersion` | string | 必须等于 OpenAPI `info.version`，SemVer；M1 初始值固定为 `1.0.0` |
| `contractFingerprint` | string | DR-01-004 的完整值 |
| `capabilities` | array<string> | 从 OpenAPI 中受治理的业务 operationId 生成；唯一、按字典序；M1 允许空数组；必须与 IMPL-01-014 相同 |
| `sourcePath` | string | 固定仓库相对路径，不接受绝对路径 |
| `sourceSha256` | string | 64 位小写十六进制，与 fingerprint 摘要相同 |
| `javaGenerator` | object | 工具坐标、固定版本、配置摘要 |
| `pythonGenerator` | object | 工具包、固定版本、配置摘要 |
| `fixtureManifestSha256` | string | 第 8.2.4 节 fixture manifest 的 64 位小写 SHA-256 |
| `generatedArtifacts` | array | Python 模型与制品元数据记录文件 SHA-256；Java 构建产物记录相对路径排序后的 tree SHA-256；不得记录 `target` 绝对路径 |

锁文件不得写时间戳、主机名、临时目录或绝对路径。生成器版本变化即使 Schema 不变，也必须重新生成、更新锁文件并执行完整契约测试。

#### 8.1.3 正常流程

1. 契约维护者只修改 OpenAPI 根及配套 fixture。
2. 规范化检查拒绝 BOM、CRLF、重复 JSON key、悬空 `$ref`、非 3.1 版本和非 SemVer `info.version`。
3. 契约制品编排器固定调用第 8.5 节 Java/Python 工具链，分别写入临时目录并运行严格编译/解析测试。
4. 编排器从规范化源生成 `contractVersion`、`contractFingerprint` 和有序 capability 制品元数据，再计算 Python/Java 产物摘要及 fixture manifest 摘要并形成 lock；不得从运行环境或手写常量补值。
5. 第二次生成与第一次逐字比较；不一致则返回 `CONTRACT_GENERATION_NON_DETERMINISTIC`。
6. 显式 update 模式以原子替换写入允许提交的 Python 模型、制品元数据和 lock；普通 check 模式禁止修改工作区。
7. CI 在干净检出上重生成并比较，任何差异阻止合并。

### 8.2 公共契约范围和贡献协议

#### 8.2.1 设计规则

| 规则编号 | 规则 | 责任主体 | 触发条件 | 输出/状态效果 |
|---|---|---|---|---|
| DR-01-005 | Runtime readiness 必须同时比较 version、精确 fingerprint 和所需 capability；任何一项不满足均不可路由 | Java Compatibility Gate | 实例发现、定期探测、调用前重验 | allow/reject，不降级放行 |
| DR-01-006 | 公共错误使用封闭错误码和统一封套；不得把异常类名、堆栈、Prompt、密钥或任意 provider 文本作为契约字段 | OpenAPI 所有者 | 任一失败响应 | 稳定、安全错误 |
| DR-01-007 | OpenAPI 只表达跨运行时 wire 结构；Java 持久状态、权限决定和确定性终检不转移给 Python | 各专题所有者 | Schema 贡献 | 保持责任边界 |
| DR-01-008 | Route/Plan/DOCUMENT/Tool 业务字段必须由对应已评审 L2 提交契约变更清单；没有权威输入时不得预建 | 关联 L2 + 01 维护者 | 新能力或字段 | 接受或 `DESIGN_INPUT_UNRESOLVED` |
| DR-01-009 | 错误码、HTTP 映射和安全 message 模板由 OpenAPI 固定；Runtime 不输出重试建议，Java 不依据任意异常文本分支 | OpenAPI 所有者、Java 调用方 | 失败响应 | 确定性错误或安全通用错误 |
| DR-01-010 | 发布和回滚以精确 fingerprint 匹配的 Java+Runtime 完整配对为单位；不得跨蓝绿池或只回滚一端 | 发布责任人 | 新指纹上线或回退 | 同指纹通信，否则失败关闭 |
| DR-01-011 | capability 贡献必须同时具备责任 L2、Schema、fixtures、兼容分类和验证；缺项不得进入唯一源 | 关联 L2 + 01 维护者 | 能力契约变更 | 接受或 `CONTRACT_CHANGE_UNGOVERNED` |
| DR-01-012 | 生成、测试、CI 和运行依赖均不得读取 `*_alpha`，也不得建立平行 OpenAPI 根或平行契约 workflow | 契约维护者 | M1 实施及每次变更 | 保持 P0 隔离和单一门禁 |
| DR-01-013 | Java 与 Python 对不可信 JSON 必须先按各自制品内、由唯一 OpenAPI 源生成的 Draft 2020-12 Schema 校验，再绑定 generated model；Java 另执行 Bean Validation。任一步失败均为 `CONTRACT_PAYLOAD_INVALID`，不得进入兼容门禁或下游调用 | `agent-service` Java 调用边界、`agent-runtime` 契约边界 | 解析 readiness、error 或后续业务请求/响应 | 严格 generated model 或确定性拒绝 |

#### 8.2.2 M1 公共 Schema

M1 只冻结不依赖后续业务专题的公共结构：

| Schema | 必填字段 | 约束 |
|---|---|---|
| `ContractMetadata` | `contractVersion`、`contractFingerprint`、`capabilities` | M1 version 为 `1.0.0`；capabilities 为唯一、稳定、按字典序输出的业务 operationId 列表，M1 尚无业务 operation 时允许空数组；不得含凭据或动态模型名称 |
| `RuntimeReadiness` | `status`、`metadata`、`reasons` | `status` 仅 `CONTRACT_READY`/`CONTRACT_NOT_READY`；reasons 仅 `CONTRACT_METADATA_INVALID`、`CONTRACT_MODEL_LOAD_FAILED`、`CONTRACT_CAPABILITY_INCONSISTENT`，ready 时为空 |
| `RuntimeError` | `code`、`message`、`diagnosticId`、`contractVersion`、`contractFingerprint` | `message` 是安全模板；可选且非 nullable 的 `requestId`、`executionId`、`attempt` 仅在调用边界已可信提取时返回，`attempt >= 1`；解析前失败时省略；不包含 `retryable` |

建议的 M1 元数据接口为 `GET /internal/runtime/v1/contract-readiness`，只返回上述 `RuntimeReadiness`。它只证明契约制品自洽，不证明模型、检索、数据库或整体服务健康。它是内部管理契约，不得暴露到外部 Gateway；认证、管理端口以及完整服务 readiness 的聚合方式由 Runtime Tool 安全/部署专题冻结，在其完成前该接口不得接入活动服务发现。

| 条件 | HTTP | 响应 | 语义 |
|---|---:|---|---|
| 契约自检完成 | 200 | `RuntimeReadiness` | 用 `status` 区分 `CONTRACT_READY`/`CONTRACT_NOT_READY`，避免探测器把受控不就绪误作传输故障 |
| 监听器已启动但无法构造受控响应 | 500 | `RuntimeError` / `RUNTIME_INTERNAL_ERROR` | 仅安全 message 与 diagnosticId；不得返回部分元数据 |
| 未认证或不在管理网络 | 由安全/部署 L2 冻结 | 不在 M1 接流量 | 01 不推测 header、端口或网络策略 |

#### 8.2.3 能力契约贡献清单

每个后续专题至少提交以下完整变更，缺一项不得合入 OpenAPI：

1. operationId、调用方向、触发条件和唯一责任人；
2. request/response/error Schema 的 required、nullable、default、enum、unknown 和边界语义；
3. `requestId`、`executionId`、attempt、absolute deadline、取消与迟到结果所需字段；
4. 权限/安全投影字段的数据分类和禁止日志清单；
5. 正常、边界、未知字段、未知 discriminator、超限和错误 fixture；
6. SemVer 分类、旧/新制品矩阵、灰度顺序和回滚条件；
7. Java/Python 双端契约测试和对应验证命令。

贡献清单只把已获批准的业务语义编入 OpenAPI，不把 01 变成生命周期、权限或 DOCUMENT 的第二设计权威。

#### 8.2.4 Golden fixture 权威与清单

fixture 唯一入口固定为建议新增目录 `agent-api/src/test/resources/contract/fixtures/agent-runtime/`，其中 `manifest.json` 是人工维护的用例清单。每项必须包含 `id`、`direction`、仓库相对 `file`、该文件内容的 `sha256`、`expectation`（`ACCEPT`/`REJECT`）和拒绝用例的 `expectedCode`；路径不得越出该目录。`fixtureManifestSha256` 锁定 manifest 本身，每项 `sha256` 锁定其引用内容；任一摘要不一致均按 drift 失败。Java 与 Python 测试必须读取同一清单和同一 JSON 文件，不得各建一套等价样例。

M1 至少包含 metadata/readiness/error 正例，以及 extra field、missing required、unknown enum、optional 非 nullable 显式 null、fingerprint mismatch、capability missing 和安全错误封套负例。M1 尚无业务 union，未知 discriminator 由不进入权威源的隔离 conformance Schema 验证；首个获批 union 进入唯一源时，必须把缺失/未知 discriminator 和 subtype 不匹配加入同源 fixture，未完成不得贡献该 union。fixture 变更必须同步 `fixtureManifestSha256`；真实请求、密钥、Prompt、权限表达式和业务正文禁止进入样例。

### 8.3 版本、兼容、readiness 与路由

#### 8.3.1 版本规则

| 变化 | SemVer | 示例 | 兼容判断 |
|---|---|---|---|
| 仅描述、示例、生成器或非 wire 规则变化 | patch | 文案修正、生成器升级 | fingerprint 改变，仍须新配对制品 |
| 向后兼容的可选字段/新 capability | minor | 新 optional 字段 | 只有双方生成自同一 fingerprint 才直接通信 |
| 删除/重命名字段、optional→required、收紧范围、改变 enum/错误/语义 | major | 删除 enum 值 | 必须新主版本和独立蓝绿池 |

本文采用“精确指纹兼容”，不让旧消费者依赖忽略未知字段。SemVer 用于变更治理和人工审计，fingerprint 才是运行时路由依据。

#### 8.3.2 readiness 正常流程

1. Runtime 构建时把 lock 中 version、fingerprint 和已实现 capabilities 注入只读制品元数据。
2. Runtime 只有在生成模型加载成功、lock 元数据一致且 capability 与已实现 operation 对应时返回 `CONTRACT_READY`；外部依赖健康不由该状态表示。
3. Java 读取 readiness，校验响应结构、version 格式、fingerprint 精确相等和所需 capability 存在。
4. 任一校验失败时实例进入不可路由集合，记录安全诊断，不尝试业务请求。
5. 没有兼容实例时 Java 返回 `RUNTIME_CONTRACT_INCOMPATIBLE` 或 `RUNTIME_CAPABILITY_UNAVAILABLE`；是否重试由后续生命周期 L2 按总 deadline 决定，Runtime 响应不携带重试建议。

#### 8.3.3 Java 兼容判定契约

`RuntimeCompatibilityGate.evaluate(expected, actual, requiredCapability)` 是无 I/O、无缓存、无重试的纯判定边界；`expected` 和 `actual` 均使用 IMPL-01-004 生成的 `ContractMetadata`，不得在 `agent-service` 手写同义 wire DTO。`expected` 只能由打包在 `agent-api` 制品 classpath、且对应 IMPL-01-002 的 lock resource 加载；`actual` 只能来自已通过 OpenAPI 严格解析的当前 readiness 响应。`requiredCapability` 在仅检查基础契约时允许省略，在选择业务调用实例时必须是非空 operationId。

| 值对象/枚举 | 字段或值 | 约束 |
|---|---|---|
| generated `ContractMetadata` | `contractVersion`、`contractFingerprint`、`capabilities` | IMPL-01-004 生成；字段含义与 M1 OpenAPI 完全一致；capabilities 非空值、无重复、按字典序；不得建立手写同义类型 |
| `RuntimeCompatibilityDecision` | `status`、`reason`、`expected`、`actual`、`requiredCapability` | `status` 仅 `ALLOW`/`REJECT`；ALLOW 时 reason 固定 `COMPATIBLE`，REJECT 时使用下述封闭原因；不得携带响应正文或凭据 |
| `RuntimeCompatibilityReason` | `COMPATIBLE`、`METADATA_INVALID`、`VERSION_MISMATCH`、`FINGERPRINT_MISMATCH`、`CAPABILITY_MISSING` | 未知值和空值按 `METADATA_INVALID` 失败关闭，不得映射为兼容 |

判定顺序固定为：结构/格式与 capability 集合规范性 → version 精确相等 → fingerprint 精确相等 → required capability 存在。首个失败原因即为 decision reason，保证日志、指标和测试一致。调用方只把 `ALLOW` 候选放入可路由集合；全部候选被拒绝时，若至少一个候选仅缺 capability 则返回 `RUNTIME_CAPABILITY_UNAVAILABLE`，其他情况返回 `RUNTIME_CONTRACT_INCOMPATIBLE`。Gate 不负责候选遍历、探测新鲜度、负载均衡或重试；这些责任由后续 Runtime 客户端/部署 L2 冻结，且业务调用前必须使用该次选择所依据的最新受控 metadata 再判定一次，判定失败不得发出业务请求。

#### 8.3.4 双端严格契约解析边界

`RuntimeContractPayloadParser.parse(rawJson, schemaName, targetType)` 是 Java 消费不可信 Runtime JSON 的唯一入口。`schemaName` 只能取调用点编译时固定的 component 名称，不接受响应字段或用户输入；`targetType` 只能是 IMPL-01-004 generated model。构造时从 `agent-api` classpath 读取唯一 OpenAPI 根，解析 `components.schemas` 并为允许的 M1 Schema 编译 Draft 2020-12 校验器；资源缺失、远程 `$ref`、未知 Schema 或编译失败直接使组件构造失败。

固定顺序为：JSON 语法和尾随 token → 原始 `JsonNode` 的 JSON Schema 校验 → generated model 绑定 → Jakarta Bean Validation。任一步失败都返回内部类型化 `ContractPayloadValidationException`，对外统一映射 `CONTRACT_PAYLOAD_INVALID`，异常不得携带原始 body；调用方不得把只完成 Jackson 绑定的对象交给 IMPL-01-010。解析器无网络、无重试、无业务状态写入；编译后的 Schema 只读复用，OpenAPI 不在运行时热更新。

Python 的 `parse_contract_payload(raw_json, schema_name, model_type)` 执行同一边界：拒绝重复 key、语法错误和尾随 token，按打包的 IMPL-01-019 校验原始对象，再调用 IMPL-01-007 generated Pydantic model 的严格验证。IMPL-01-019 是 IMPL-01-008 从唯一 OpenAPI `components.schemas` 确定性派生并重写本地 `$ref` 的 Draft 2020-12 `$defs` bundle，不是第二人工编辑源；Runtime 只能通过 `importlib.resources` 读取该包资源，不得在运行时跨目录读取 OpenAPI。未知 Schema、远程 `$ref`、bundle 缺失或编译失败均失败关闭，异常不得携带原始 body。

### 8.4 错误分类和调用方可见语义

| 错误码 | 触发条件 | HTTP 建议状态 | Java 可见结果 | 状态/事务影响 | 重试性所有者 |
|---|---|---:|---|---|---|
| `CONTRACT_PAYLOAD_INVALID` | JSON、required、enum、discriminator、范围或 unknown field 无效 | 400 | 确定性拒绝 | 不进入模型/Tool；无远端副作用 | 不可重试 |
| `CONTRACT_VERSION_UNSUPPORTED` | 请求 version 不受 Runtime 支持 | 409 | 实例不可用于该调用 | 不进入业务处理 | Java 重新选兼容实例，不重发同实例 |
| `CONTRACT_FINGERPRINT_MISMATCH` | version 相同但 fingerprint 不同 | 409 | 安全告警并摘除实例 | 不进入业务处理 | 不可对该实例重试 |
| `RUNTIME_CONTRACT_INCOMPATIBLE` | Java 没有找到 version/fingerprint 均精确匹配的 Runtime | 503 | 对外返回稳定不可用语义 | 不发起 Runtime 业务调用 | 后续生命周期 L2 可在原 deadline 内重新探测，不放宽匹配 |
| `RUNTIME_CAPABILITY_UNAVAILABLE` | readiness 不含所需 capability | 503 | 能力当前不可用 | 不创建新的远端副作用 | 后续生命周期 L2 |
| `DEADLINE_EXCEEDED` | absolute deadline 已到或处理超时 | 504 | 超时失败 | Java 栅栏决定终态；迟到结果拒绝 | 后续生命周期 L2 |
| `RUNTIME_CANCELLED` | 收到有效取消并停止 | 409 | 取消结果 | Java 独占终态权威 | 不自动重试 |
| `RUNTIME_INTERNAL_ERROR` | 未分类内部缺陷 | 500 | 安全通用错误 + diagnosticId | 不泄漏内部异常 | 后续生命周期 L2 |

`RuntimeError.message` 只能从代码对应的固定安全模板产生。Provider 错误、解析异常和堆栈只进入受控诊断，普通日志不得包含请求正文、历史、上下文、凭据或生成结果。

### 8.5 生成、更新与检查模式

M1 依赖已由 `M1-AUTH-20260721-01` 授权并固定如下；POM、Python 项目元数据和 contract lock 必须记录同一完整版本，编排器不得使用 PATH 或网络解析出的“最新版本”。

| 端 | 固定工具身份 | 固定语义参数 | 采纳门禁 |
|---|---|---|---|
| Java generation | `org.openapitools:openapi-generator-maven-plugin:7.24.0`，`generatorName=java`、`library=restclient`，仅生成 models | `useJakartaEe=true`、`useBeanValidation=true`、`failOnUnknownProperties=true`、`legacyDiscriminatorBehavior=false`、`useOneOfInterfaces=true`、`useSealedOneOfInterfaces=true`、`useOneOfDiscriminatorLookup=false`；生成包 `com.dylan.baseline.agent.api.runtime.generated`；关闭时间戳、API、客户端、文档、测试和 supporting files；输出只在 `target/generated-sources/openapi/java` | Java 25 编译；相同输入两次 tree hash 一致；M1 不用生成 POJO 替代 JSON Schema 校验 |
| Java strict validation | `com.networknt:json-schema-validator:2.0.4`（Jackson 2 线）+ Spring Boot 3.5.10 管理的 Jakarta Bean Validation | 原始 JSON 按固定 component Schema 校验后才绑定 generated model；ObjectMapper 拒绝未知字段、未知 enum、无效 subtype 和尾随 token；随后显式 `Validator.validate()`；Schema 缺失/编译失败使组件构造失败 | 同源 fixture 对 required、optional 非 nullable、enum、范围、格式和 closed object 的 Java 结论与 Python 一致 |
| Python | `datamodel-code-generator==0.69.0`，输出 `pydantic_v2.BaseModel`；运行依赖 `pydantic==2.13.4`、`jsonschema==4.26.0` | Python 3.12；原始对象由 `Draft202012Validator` + format checker 校验后才绑定 Pydantic；未知字段拒绝；显式 discriminator；稳定 enum；关闭时间戳；wire lowerCamelCase 通过 alias 保持，禁止语义补丁 | Python 3.12/Pydantic v2 解析全部同源 fixture；重生成字节一致；optional 非 nullable 不得被 Pydantic 的 `None` 默认行为放宽 |
| Python packaging | `setuptools==83.0.0` + `setuptools.build_meta` | `src` layout；显式把 IMPL-01-014 声明为 `agent_runtime.contracts` package data；构建时不生成或改写契约 | 离线构建 wheel 后从临时安装目录使用 `importlib.resources` 读取 metadata，内容与工作区/lock 一致 |

上述完整版本只能在依赖已预先提供的环境中运行同一最小 conformance suite。suite 至少覆盖 closed object、missing required、optional 非 nullable、nullable、enum unknown、discriminator unknown、RFC3339 UTC、整数毫秒、alias 序列化和 malformed metadata。Java generated model 只承担绑定和类型承载，JSON Schema validator 承担 OpenAPI 3.1 结构语义，Bean Validation 承担生成注解的对象级复核；不得删除任一阶段以换取通过。首个 union 必须使用“公共基类 String discriminator + subtype `const` + 显式 mapping + 封闭属性”的隔离 PoC 证明 Java 25 可编译和双端拒绝未知 subtype 后才可入源。后续升级按契约变更处理；工具升级造成的产物差异即使 wire Schema 不变也必须提升 patch、形成新 fingerprint 配对并执行完整测试。

| 模式 | 允许写入 | 触发方式 | 失败行为 | 幂等/安全重跑 |
|---|---|---|---|---|
| `check` | 无 | 默认本地/CI | 任一漂移非零退出 | 可重复、工作区不变 |
| `update` | IMPL-01-007 + IMPL-01-014 + IMPL-01-019 + IMPL-01-002 | 显式参数，开发者本地 | 临时生成/校验成功前不覆盖 | 同源重复执行字节一致 |
| Java compile | `target/generated-sources/**` | Maven 生命周期 | 生成或编译失败阻断 build | 输出为构建目录，可清理重建 |

生成脚本不得自动安装依赖、创建 `.venv`、访问网络、读取生产配置或调用模型。所有生成依赖必须通过 Maven/pluginManagement 或 Python 锁定开发依赖预先提供。

## 9. 条件设计

### 9.1 接口与跨语言契约设计

- OpenAPI 版本固定为 3.1.x；根文件不允许远程 `$ref`，避免构建时网络和供应链漂移。
- object 默认 `additionalProperties: false`；只有明确 map 语义的字段可局部开启并定义 value Schema。
- required 字段不得同时 nullable；optional、nullable 和 default 是三个独立语义，禁止互换。
- wire enum 使用稳定字符串，未知值拒绝；禁止 Java ordinal 和 Python 宽松字符串回退。
- union 使用公共基类上的 String discriminator、subtype `const`、显式 `oneOf` mapping 和封闭属性；不得把各 subtype 的 discriminator 生成为不兼容枚举 getter。缺失、未知、多个 subtype 同时匹配或 subtype 不匹配均由原始 JSON Schema 校验为 `CONTRACT_PAYLOAD_INVALID`。
- 时间使用 RFC 3339 UTC `date-time` 且必须带 `Z`；duration 使用整数毫秒并以 `*Ms` 命名；计数为非负整数。
- 标识符按字段 Schema 固定 UUID 或受限字符串；不得由生成器在 Java/Python 两端推断成不同含义。
- JSON 字段统一 lowerCamelCase；Python 通过 alias 暴露 wire 名，内部 snake_case 不改变序列化。
- 请求和响应的未知字段均拒绝；兼容发布使用精确指纹配对，不用宽松解析换取滚动升级。

### 9.2 数据与生命周期设计

本文不新增数据库、索引、缓存或消息主题。OpenAPI、lock、fixtures、提交的 Python generated model、`contract_metadata.json` 和生成的 `contract_schema.json` 是版本控制工件；Java generated source 位于 Maven `target`，不提交。Java 从 `agent-api` 制品 classpath 读取 lock/OpenAPI，Python 从自身包资源读取生成的 metadata/schema bundle；二者都不得在运行时跨仓库目录读取源文件。生产运行时不得动态读取 OpenAPI 来决定权限、业务语义或状态迁移。

### 9.3 状态、事务与一致性边界

- 生成过程是构建期文件转换，不参与业务事务。
- update 使用临时文件、完整校验、原子替换；失败保持旧工件不变。
- Runtime readiness 是派生运行状态，不是 Java 执行状态权威。
- Java 调用 Runtime 时的事务、重试、取消和栅栏由生命周期 L2 决定；01 只保证必要字段进入后续贡献清单。
- Java/Python 不通过双写保持契约一致，而是通过同一源、同一提交、lock 和 CI 闭环。

### 9.4 权限、安全、风控与审计设计

- OpenAPI 和 fixtures 不得包含真实密钥、token、用户正文、权限表达式或业务敏感样例。
- readiness 只暴露版本、指纹、capability 和封闭原因码，不暴露依赖地址、模型名称、堆栈或配置值。
- Runtime/Tool 身份认证和短期凭据由安全专题定义；01 不默认任何 header 名称或密钥格式。
- 每次契约变更审计至少记录 Git commit、旧/新 version、旧/新 fingerprint、变更分类、生成器版本和验证结果。
- 未知 Schema、未知 capability 或元数据不一致一律失败关闭，不允许兼容模式开关绕过。

### 9.5 性能、容量与资源预算

M1 构建期目标是生成与 drift 检查可在普通开发机和 CI 内稳定完成；不以删除安全约束换取速度。运行时 readiness body 应为小型固定结构且不得包含完整 OpenAPI。具体延迟、并发、探测频率和缓存期限由部署/性能 L2 量化，因此不作为本文生产承诺。

### 9.6 发布、迁移与回滚

1. 契约源、lock、generated Python model、Python `contract_metadata.json`、Java 生成配置、fixtures 和测试必须在同一提交内闭合。
2. 新 fingerprint 的 Python Runtime 先部署到隔离的蓝绿池，但对旧 Java 保持不可路由。
3. 新 Java 只绑定相同 fingerprint 的 Runtime 池；旧 Java 继续绑定旧池，禁止跨池随机路由。
4. 验证通过后切换 Java 流量；观察期内保留上一整组 Java+Runtime 制品。
5. 回滚以“同 fingerprint 的 Java+Runtime 完整配对”为单位，不只回滚一端。
6. major 变化不得共享实例池；minor/patch 也不放宽精确指纹规则。

### 9.7 日志、监控与告警

| 事件/指标 | 最小字段 | 禁止字段 | 告警条件 |
|---|---|---|---|
| `contract_generation` | commit、version、fingerprint、generator、result | 绝对路径、环境变量 | CI 生成失败或不确定性 |
| `runtime_contract_probe` | instance 摘要、expected/actual version/fingerprint、capability、result | 密钥、完整配置 | 连续不匹配或兼容实例数为 0 |
| `runtime_contract_reject_total` | reason、expected version、capability | 请求正文、Prompt、上下文 | 任一 fingerprint mismatch 立即告警 |
| `runtime_compatible_instance_count` | version、fingerprint、capability、count | 实例凭据 | 活动能力 count=0 |

告警后只摘除不兼容实例并阻止新调用，不自动回退安全校验或切换到 alpha。
