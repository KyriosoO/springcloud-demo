## 3. 背景、目标与范围

### 3.1 背景与问题

当前根目录中的七个 `agent-*` 与两个 `es-*` 均为旧实验资产，但仍占用目标项目名称。八个 Java 项目同时进入 `serviceCenter` Maven 反应堆，`document-provider-adapter` 和 `employee-service` 仍直接编译依赖旧 API 类型；统一启动脚本会启动 `agent-runtime`、`agent-service` 和 `es-query-service`；旧服务还携带数据库初始化、迁移与 ES Alias 写入能力。若只改目录名而不切断根构建、依赖、CI 与运行入口，会使历史资产继续成为事实权威；若直接让两个消费者解析到全新空 API，根反应堆又会因旧类型缺失而失败。

本设计只解决阶段 0 的实施落点隔离：把九个完整旧目录转为不构建、不运行、不发布的 `_alpha` 历史资产，在原名位置建立不含业务实现的目标骨架，并以可失败验证证明历史资产未进入根 POM、活动依赖、CI、运行或写入权威。它不设计新业务契约，不迁移旧业务代码，也不擅自改造两个外部消费者；后者作为实施前置阻塞显式保留。

### 3.3 范围内

- 九个项目目录的整体历史归档、八个 alpha POM 构建标识隔离、根反应堆仅保留同名新目标模块的规则；
- `document-provider-adapter`、`employee-service` 对旧 API 类型的当前依赖发现、阻塞登记和后续决策门禁；
- 新同名 Java/Python 空骨架的文件边界、构建和启动门禁；
- 默认启动脚本对旧/新 Agent、Runtime、ES 服务的隔离；
- 旧 CI 工作流的 alpha 证据归档、新目标 CI 入口和全仓引用分类；
- alpha 服务注册名与目标服务 discovery/config client 禁用策略；
- 旧状态表、迁移 SQL、ES 索引/Alias 和忽略文件的保护规则；
- 前置检查、执行顺序、失败恢复、验证证据和后续专题解锁条件。

### 3.4 范围外

- 本轮实际移动目录、修改 POM/代码/配置/脚本、创建骨架或安装依赖；
- 修改 `document-provider-adapter`、`employee-service` 的代码、POM、公共契约或根模块资格；
- 新 Java↔Python、Agent↔检索或外部业务 API 的字段与兼容设计；
- 旧 Agent 业务代码向新项目迁移；
- 数据库 DDL/DML、Flyway 执行、索引创建、Alias 切换或生产数据删除；
- 启动 alpha 服务、恢复旧生产流量或授予 alpha 生产回滚资格；
- 创建分支、提交、推送、PR 或修改 Git 历史。

### 3.5 非目标

- 不以复制旧目录后删除部分文件的方式建立新项目；
- 不让新项目暂时依赖 alpha，再承诺以后清理；
- 不让任何活动根模块、CI 或发布任务临时依赖/构建 alpha 来维持全仓构建；
- 不为了保持旧功能可运行而让默认启动链继续启动 alpha；
- 不把 P0 构建成功解释为业务能力、目标质量或生产就绪；
- 不在本专题冻结后续 01、03、生命周期、安全或检索契约细节。

| BASE-005 | `scripts/start-all-services.ps1` 默认启动 `agent-runtime:9230`、`agent-service:9220`、`es-query-service:9201` 并等待两个 Java 注册名 | 隔离后继续默认启动会让旧资产或空骨架取得流量 |
| BASE-006 | 旧 Java 注册名为 `agent-service`、`es-query-service`；Gateway、Feign 和文档提供方仍含原名调用位置 | P0 不能宣称调用方迁移完成，只能让目标服务保持不注册 |
| BASE-007 | `agent-service` 含 17 个建表对象；`es-query-service` 含 9 个建表对象（V1、V4 及 V5 的 7 个），部分 `document_*` 表名重叠 | P0 不得启动新骨架的数据自动配置或迁移 |
| BASE-008 | `scripts/chinatax_v2/` 含 `agent-doc-tax-policy-v2-*`、`agent-doc-tax-policy-v3-dataopt-*` Alias/索引写入入口 | P0 不执行、不复制、不改写这些物理资产 |
| BASE-009 | `agent-runtime/.env`、`.venv`、各项目 `target/` 等忽略/未跟踪内容存在；`.env` 内容未被读取 | 目录移动必须整体保留且不得把秘密复制到新 Runtime |
| BASE-010 | 编写起点 Git 工作区干净，HEAD 为第 1 节记录值 | 后续实施必须重新核验，不能依赖本次快照 |
| BASE-011 | 跟踪文件 `.github/workflows/agent-contract.yml` 监听原名项目路径，并引用旧 Runtime 的依赖文件和测试 | 目录重命名后若不拆分，旧证据 CI 会失联，而新目标路径会被旧测试错误验证或直接失败 |
| BASE-012 | `serviceCenter/pom.xml` 向子模块直接继承 Spring Cloud Starter/Config 依赖，并配置 Spring Boot Maven Plugin | 新建空库若只声明父 POM，会带入运行时依赖，且空 jar 可能被重打包规则处理 |

|---|---|---|---|

### 7.3 内聚与耦合判断

目录、根构建、活动依赖、CI、默认启动和资源写入共同决定“谁是实施基线”，必须作为一个 P0 批次验证；拆给各业务专题会产生部分隔离状态。alpha 没有任何临时兼容边。两个现有消费者的旧类型依赖不能通过 alpha 延续，也不能由空骨架伪兼容，必须在 P0 变更前由独立设计选择“迁移到已冻结的新契约”或“退出活动根模块”等方案并取得授权。新目标骨架不承担旧兼容，因此不会把旧接口提前固化为新权威。

## 8. 详细功能与流程设计

### 8.1 前置冻结与排他执行

#### 8.1.1 设计规则

| 规则编号 | 规则 | 责任主体 | 触发条件 | 输出/状态效果 |
|---|---|---|---|---|
| DR-001 | 02 必须先独立评审通过，实施任务再精确授权目录、POM、配置、脚本、验证和必要删除动作 | 用户 + 实施责任人 | 准备执行 P0 | 未授权时保持 `DESIGN_READY` |
| DR-002 | 执行起点必须是重新核验的干净工作区、固定 HEAD、无并行写者；分支/提交另行授权 | 实施责任人 | `Preflight` | 不满足即 `PREFLIGHT_FAILED` |
| DR-003 | Agent/ES 相关进程必须由所有者先停止；验证器只报告端口/进程，不自动终止 | 环境责任人 | 目录移动前 | 无运行句柄和写入活动 |

#### 8.1.2 输入、输出与前置条件

- 输入：通过独立评审的本文、实施授权清单、当前 HEAD、九项目清单、相关引用清单、`DB-02-001` 的已评审解决方案与完成证据。
- 必填前置：九个原名目录全部存在、九个 `_alpha` 目标目录全部不存在、工作区无未提交变更、相关服务未运行、两个外部消费者不再依赖旧/alpha 制品且不会解析到空 API。
- 输出：脱敏 `preflight` 记录，包含路径、跟踪文件数、POM/脚本引用、端口状态和上位哈希。
- `.env` 只记录“存在且未读取”，不得输出内容、哈希、长度或修改时间；`.venv`、`target/` 只记录存在性。

#### 8.1.3 正常流程

1. 重新读取四份上位文档并比对第 4.1 节哈希；不一致时停止复评。
2. 记录 HEAD、工作区状态和九项目路径；检查 `_alpha` 目的路径不存在。
3. 扫描 Maven 模块/依赖、路径脚本、注册名、端口、SQL/Flyway 和 Alias 写入口。
4. 验证 `ExternalConsumerResolutionRef` 对应方案已完成独立评审和实施，其结果既无 alpha 依赖，也不会让旧消费者编译到空目标 API。
5. 只读检查相关端口和进程；发现运行实例时由用户或服务所有者处理。
6. 生成 `PREFLIGHT_PASSED` 证据后才允许目录移动；`DB-02-001` 未关闭时必须返回 `EXTERNAL_CONSUMER_UNRESOLVED`。

#### 8.1.4 分支与边界条件

- 任一非目标工作区变更都会阻塞，而不是被暂存、清理或覆盖。
- 任一 `_alpha` 路径已存在都视为名称冲突，不合并目录。
- 发现未列出的九项目消费者时，先补充本文或重新评审，不在实施中临时猜测。
- 发现生产数据库、ES 或服务实例只能做经授权的只读检查，不允许为 P0 修改外部状态。

### 8.2 旧项目整体隔离与构建图重写

#### 8.2.1 设计规则

| 规则编号 | 规则 | 责任主体 | 触发条件 | 输出/状态效果 |
|---|---|---|---|---|
| DR-004 | 九个目录必须按第 6.3 节一一整体移动，`_alpha` 后缀追加在完整项目名末尾 | 实施责任人 | `PREFLIGHT_PASSED` | `LEGACY_ASSETS_ARCHIVED` |
| DR-005 | 八个 alpha POM 仅将自身 artifactId/name 及九项目内部依赖改为第 6.3 节 `_alpha` 标识，包名、业务类型、源码、配置、测试、脚本和忽略内容不改；该元数据隔离不授予构建资格，仍禁止根 POM/profile、构建、安装、发布、运行或 CI 调用 | 历史资产责任人 | 目录移动完成 | 历史业务内容完整、GAV 不冲突且无活动资格 |
| DR-006 | `serviceCenter/pom.xml` 不得出现任何 `_alpha` 模块/profile；现有原名模块路径在重建后只属于八个新目标 Java 项目。任何活动模块不得依赖 alpha；两个现有消费者的解决证据是 Preflight 硬前置，不在 02 中临时改依赖 | 构建责任人 | Preflight 与目标骨架创建 | `TARGET_REACTOR_ISOLATED` |

#### 8.2.2 执行顺序

1. 按第 6.3 节固定顺序整体移动九个目录；每组移动前以 `BeginStage` 持久记录意图，移动并核验后以 `Checkpoint` 原子记录完成状态。
2. 只修改八个 alpha POM 的自身 artifactId/name 和九项目内部依赖为 `_alpha`；核对除此以外的历史内容与移动前清单一致，不构建 alpha，也不修改两个外部消费者。
3. 在原名路径显式创建九个新目标骨架；`serviceCenter/pom.xml` 保留原名模块路径语义且不得增加任何 `_alpha` 条目或 profile。
4. `agent-runtime_alpha` 的 `.env`、`.venv`、缓存和生成物随目录移动但不进入新项目；不读取、不复制、不提交本地秘密。

#### 8.2.3 边界条件

- 目录移动必须保持跟踪文件总数一致；忽略文件只验证仍位于 alpha 目录，不进入证据内容。
- alpha Maven 变更必须限定为自身 artifactId/name 与九项目内部依赖的机械 `_alpha` 命名空间化；不得顺带升级依赖、改插件、包名或业务配置。即使坐标已隔离，也禁止以独立 `mvn install/deploy` 规避历史资产门禁。
- 新目标构建绝不反向依赖 alpha；活动根模块也不得依赖 alpha。
- 两个现有消费者不得临时切到 alpha，也不得以复制旧类型到新空 API 的方式解除阻塞。

## 9. 条件设计章节

### 9.1 接口、构建、项目与运行契约

- alpha Maven 坐标统一使用 `_alpha` artifactId，但不得由根 POM、活动依赖、CI、安装或发布解析；新目标坐标保持原名。
- Java 包名不是 P0 项目标识，不在 alpha 中批量改包；同包名只允许存在于互不依赖的不同制品。
- alpha 服务配置中的旧注册名保持历史原样但永不加载；目标注册名保持原名但默认不注册。
- 本专题不改变任何业务 API 字段、HTTP 路径或错误模型。现有业务调用方只有在后续契约专题通过后才能切到新目标制品/服务。

### 9.2 数据与证据生命周期

阶段 0 的持久阶段日志与最终报告使用同一建议新增固定文件 `docs/design/agent/evidence/baseline-isolation/p0/baseline-isolation-report.json`。首次成功 `Preflight` 在任何项目变更前创建有效 JSON；后续模式以同一 `runId`（UTC 时间 + HEAD 短哈希）更新，不生成动态权威路径。报告至少包含 `schemaVersion`、`runId`、`sourceCommit`、上位哈希、授权范围摘要、`externalConsumerResolutionRef`、`status`、`currentStage`、`pendingStage`、九项目 `items`、`stageTransitions`、`checks`、`referenceClassifications`、`esMigrationCandidates`、失败代码和未决项。每个 `items[]` 至少记录 `itemId`、`actionType`、`sourcePath`、`destinationPath`、`createdPaths`、`preState`、`postState` 和 `result`；`preState/postState` 只保存跟踪文件数、忽略资源存在性布尔值及非秘密文本文件 SHA-256，`createdPaths` 保存本次新建文件的精确相对路径和创建后 SHA-256，供恢复前防误删核对。

每次更新先在同目录写完整的 `baseline-isolation-report.json.tmp`，完成 JSON 解析和必填字段自检后以原子替换发布；进程级独占文件锁失败时不得写入。`BeginStage` 必须在项目动作前记录 `STARTED`、目标项和预期效果；`Checkpoint` 只在动作后置条件通过后记录 `COMPLETED`。启动时若最后一个有效报告含未闭合 `STARTED`、报告与现场路径不一致或仅遗留临时文件，状态必须为 `RECOVERY_REQUIRED`，只允许 `RecoveryCheck` 输出差异和建议反向顺序，不得自动续跑、删除或回滚。报告及临时文件均禁止包含密钥、`.env` 摘要、完整配置、正文、业务结果、数据库行或 ES 文档。

旧表、索引、Alias 和本地忽略文件的保留周期不由 P0 决定。alpha 物理删除必须等所有引用为零、后续专题完成替代、独立删除授权和恢复证据具备后另行执行。

### 9.3 并发、一致性与幂等

P0 是版本库内的一次有序变更，不使用数据库事务、分布式锁或生产全局锁。排他性由干净工作区、单一实施责任人、停止相关进程、报告文件独占锁和逐动作持久阶段日志保证。验证可重复执行；目录移动和骨架创建不是盲目幂等操作，重复执行必须因当前状态不匹配而失败，不允许覆盖或合并。

### 9.4 权限、安全与审计

- 目录移动、文件修改、精确删除新骨架和 Git 操作分别受实施授权约束。
- 不自动终止用户管理的进程，不访问生产写凭据，不执行数据库或 ES 写命令。
- `.env`、凭据和完整外部配置既不读取也不进入证据；目录整体移动只改变位置。
- 验证日志记录操作者、HEAD、映射、检查结果和安全摘要；不记录业务数据或秘密。

### 9.5 性能与容量

不适用生产 SLO：P0 不提供业务流量。只要求验证命令在单次本地/CI 作业内有界完成；若根反应堆耗时过长，可先跑目标模块验证，再跑完整反应堆，但两者均须通过才能验收。

### 9.6 发布、兼容与回滚

| 阶段 | 发布/兼容策略 | 回滚动作 | 回滚后验证 |
|---|---|---|---|
| 目录移动前 | 无运行变化 | 不适用 | 前置检查重跑 |
| 仅目录已移动 | 不启动任何 Agent/ES | `RecoveryCheck` 核对现场后，按 `COMPLETED` 项反向移动 | 九个原名恢复、无 alpha 残留 |
| 历史入口已归档 | alpha 不构建、不运行；外部消费者方案已在 P0 前独立完成 | 先恢复 alpha POM 原标识和本次移动的旧脚本/CI 文本，再反向移动项目目录；不回退外部消费者的独立变更 | 旧项目路径、POM 标识和旧活动入口恢复，外部消费者状态保持其独立授权结果 |
| 新骨架已建 | 新骨架 discovery/数据能力关闭 | 仅删除报告 `items` 中由本次运行创建且现场摘要匹配的文件，再恢复脚本/CI与目录 | 无同名冲突、旧内容完整 |
| `P0_VERIFIED` 后 | 默认仍无 Agent/ES 流量 | 回退须重新授权，不把 alpha 自动上线 | 独立回滚评审和全量验证 |

本设计不要求自动 Git 提交。若用户另行授权形成提交，后续回滚优先使用经评审的反向提交；禁止脚本自行 `reset --hard`、`clean`、覆盖用户变更或删除生产资产。

### 9.7 日志、监控与告警

P0 只产生实施日志和验证报告。阻塞性条件包括：工作区变化、上位哈希漂移、映射不完整、阶段日志未闭合、跟踪引用未分类、CI 权威混用、新目标依赖 alpha、默认启动链包含新旧 Agent/ES、目标骨架含 DB/ES/业务代码、外部状态异常变化。任一条件触发时退出非零并保留脱敏证据，不自动修复。
