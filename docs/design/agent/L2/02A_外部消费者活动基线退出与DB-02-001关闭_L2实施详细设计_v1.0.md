## 3. 背景、目标与范围

### 3.1 背景与问题

`employee-service` 拥有员工表、变更审批和消息处理等业务责任，但其 ES 能力仍编译依赖旧 `es-query-api`。P0 将把 `es-query-api` 迁入 alpha 历史路径并以原名建立空骨架；若 `employee-service` 仍位于活动 reactor，完整构建会解析到缺少旧类型的新空 API。将它改依赖 alpha 或向新 API 复制旧类型都会破坏绿地基线，因此 02 将其登记为 `DB-02-001`。

方案 B 不迁移员工契约，而是让 `employee-service` 暂时退出活动基线。它关闭的是“活动构建依赖边”，不是员工业务能力替代；退出后员工服务的默认可用性不再成立。`document-provider-adapter` 的隔离和目标空骨架由 02 P0 处理，不得由本方案提前移出根 reactor。

### 3.2 目标与验收行为

| 需求编号 | 目标或可观察行为 | 验收标准 |
|---|---|---|
| REQ-001 | `employee-service` 退出活动 Maven reactor | 根 `serviceCenter/pom.xml` 不再包含该 module；完整 reactor 在其缺席时构建成功，`document-provider-adapter` 仍留在 reactor 等待 P0 处理 |
| REQ-002 | `employee-service` 退出默认运行基线 | 默认脚本不启动或等待 `employee-service`；Gateway 不再路由员工接口；默认首页不再展示员工 ES/工作流入口 |
| REQ-003 | 保留业务模块事实但禁止过渡期活动化 | `employee-service` 原目录、POM、源码、配置和测试不修改、不改名；不得独立构建、安装、发布、注册或由 CI 调用 |
| REQ-004 | 不建立假兼容 | 活动图不依赖 alpha，`employee-service` 也不解析到新空 `es-query-api`；不复制旧 DTO、Feign 或检索契约 |
| REQ-005 | 显式暴露能力退出结果 | 默认首页无员工能力入口；直接访问 Gateway 员工 API/页面返回无匹配路由；不提供静默替代 |
| REQ-006 | 形成可供 P0 Preflight 核验的关闭证据 | `ExternalConsumerResolutionRef` 绑定设计、授权、HEAD、检查结果和能力影响接受记录；原子发布且状态为 `CONSUMER_EXIT_VERIFIED` 时，以 `CLOSED_FOR_P0_BY_INACTIVITY` 关闭 `DB-02-001` |
| REQ-007 | 支持受控恢复 | P0 开始前可按精确逆序恢复；P0 开始后禁止单独重新激活 `employee-service` |

### 3.3 范围内

- 从 `serviceCenter/pom.xml` 的 `<modules>` 只删除 `../employee-service`；保留 `../document-provider-adapter` 供 02 P0 原子隔离和同名空骨架替换。
- 从默认启动脚本删除 `employee-service` 启动项及 `EMPLOYEE-SERVICE` Eureka 等待项；过期 `DOCUMENT-GENERATION-ADAPTER` 等待项属于 02 P0 的 Generation 历史谱系隔离，本文不修改。
- 从 Gateway 删除路由 `emp`，停止默认暴露 `/employees/**`、`/employee-workflow.html`、`/employee-es.html`。
- 从默认首页删除 `Employee ES`、`Employee workflow` 两个按钮及仅为其服务的跳转函数，避免继续向用户展示已退出能力；保留 Agent 等其他入口。
- 核对所有活动 CI、构建、启动、注册、发布入口；当前未发现直接 CI/发布入口时只保留验证，不制造无效改动。
- 新增非修复型验证脚本和固定关闭证据，供 02 的 `ExternalConsumerResolutionRef` 使用。
- 设计实现顺序、失败语义、审计、验证和恢复门禁。

### 3.4 范围外

- 修改、删除、移动或重命名 `employee-service/` 内任何文件；将其命名为 `employee-service_alpha`。
- 在本专题中移动、重命名、构建或恢复 `document-provider-adapter`、`document-generation-adapter`；二者统一由 02 P0 治理。
- 修改 00/02 以外的 L2、L0/L1 或历史文档。
- 设计或实现新 Agent、DOCUMENT、检索、员工源数据契约。
- 修改数据库、Kafka Topic、ES 索引、Alias、Config Server 数据或生产部署。
- 提交、推送、PR、生产停机或生产流量切换。

### 3.5 非目标

- 不保证 `employee-service` 的表 API、工作流 API、ES API 或页面在默认栈继续可用。
- 不评价 `document-provider-adapter` 的目标接口可用性；它在 P0 后只是无业务能力的空骨架，具体 Provider 能力由后续专题设计。
- 不把“退出活动基线”解释为功能迁移完成、目标能力就绪或生产下线批准。

## 6. 当前实现基线与变更摘要

### 6.1 方案 B 实施前基线事实

以下条目保存方案 B 的设计和实施起点，不表示本次语义同步时的当前现场；实施后事实以第 9.8 节固定报告、第 12 节 blocker 状态和第 14 节检查结果为准。

- `serviceCenter/pom.xml` 当前包含 `../employee-service` 和 `../document-provider-adapter`；本专题只移除前者，后者必须保留到 02 P0 做原子隔离。
- `document-provider-adapter` 是旧 Agent/DOCUMENT 衍生项目；`document-generation-adapter` 是其已删除前身，当前目录只剩已忽略构建残留。两者都由 02 P0 治理，不再属于 `DB-02-001` 外部消费者。
- `employee-service/pom.xml` 直接依赖 `es-query-api`；主代码包含员工表/工作流、ES 查询/写入/重建、索引源接口和 Kafka 同步逻辑。
- `scripts/start-all-services.ps1` 默认启动 `employee-service:9210` 并等待 `EMPLOYEE-SERVICE`。脚本中的 `DOCUMENT-GENERATION-ADAPTER` 是已删除历史前身的过期等待项，由 02 P0 移除，不属于本方案。
- Gateway 路由 `emp` 将 `/employees/**`、`/employee-workflow.html`、`/employee-es.html` 转发到 `lb://employee-service`。
- 默认首页仍展示 `Employee ES`、`Employee workflow` 两个按钮并跳转到上述页面；若只删 Gateway 路由，会留下指向 404 的活动导航入口。
- `agent-adapter-employee`/`agent-service` 仍含 P0 将整体隔离的旧 Agent→employee 调用引用；`application-emp.yml` 仍保存 employee 专属配置。这些引用不形成 `employee-service` 对旧 `es-query-api` 的活动 Maven 消费边，但必须在关闭报告中单独分类，不能误报为已消失。
- 当前 Agent CI 未直接列出 `employee-service`，但会因 `serviceCenter/pom.xml` 变化触发；未发现其他显式 CI/发布入口。

### 6.2 当前问题与根因

直接问题是 `employee-service` 位于活动 reactor 且仍以旧 `es-query-api` 作为编译契约，而目标 API 必须在 P0 后重新设计。当前阶段不存在可合法迁移的目标契约，因此方案 B 通过删除该业务模块的活动资格解除编译边，不在 P0 前发明兼容接口。

### 6.3 最小变更方案

| 变更项 | 必要性 | 复用内容 | 不采用的方案及原因 |
|---|---|---|---|
| 删除根 POM 中 `employee-service` 一条 module | 解除活编译边的唯一必要动作，同时保留 Provider 供 P0 原子替换 | 现有根 reactor | 不使用 profile：会保留误激活入口；不提前删除 Provider module：会与 02 阶段责任冲突 |
| 删除 employee 默认启动和两项 Eureka 等待 | 防止默认栈启动/等待退出能力 | 现有启动脚本结构 | 不保留失败等待：会导致默认启动超时 |
| 删除 Gateway `emp` 路由 | 防止路由继续声称员工服务可用 | 现有静态路由定义 | 不指向占位服务：会形成假兼容 |
| 删除默认首页两个员工按钮和对应跳转函数 | 防止仍向用户展示已退出页面 | 现有首页其他导航保持不变 | 不保留失效链接：会把受控能力退出表现为前端故障 |
| 保留 `employee-service` 目录不变 | 保持员工业务所有权并缩小改动面 | Git 历史和现有源码 | 不重命名 alpha：它是业务模块，不属于 02 历史项目映射 |
| 新增一个非修复验证器和固定报告 | P0 Preflight 需要可机器核验的关闭证据 | 02 的证据和退出码风格 | 不只用人工结论：无法稳定关闭 blocker |

| 默认启动脚本 | 已存在 | 启动本地默认服务并验证端口/Eureka | 生产部署和能力替代 | 服务清单 → 本地进程/就绪结果 |
| Gateway 路由 | 已存在 | 暴露默认可用 HTTP 路径 | 为已退出服务提供降级替身 | 请求路径 → 路由或 404 |
| 非活动 `employee-service` | 目标过渡状态 | 保持员工业务实现与数据所有权事实 | 构建、运行、安装、发布或提供默认能力 | 只读业务源码证据 |
| 退出验证器 | 建议新增 | 非修复地核对活动边界并生成证据 | 修改 POM、脚本、路由或源码 | HEAD/授权 → 检查结果/报告 |
| P0 Preflight | 02 所有 | 重新核验 `ExternalConsumerResolutionRef`、当前干净 HEAD 和现场活动图，并决定是否允许进入 P0 | 产生或改变 `DB-02-001` 关闭事实、代替本专题实施 | 已关闭证据引用 → `PREFLIGHT_PASSED` 或阻塞 |

### 7.2 依赖方向

允许方向为：P0 Preflight → 只读解析关闭报告 → 核对当前活动图。根 reactor、默认启动/Eureka、Gateway、默认首页、CI 和发布命令不得选择或展示 `employee-service`；活动 Maven 模块不得依赖其制品。它的源码可以继续声明旧 `es-query-api` 依赖，但其路径必须被验证器标记为 `evidence_only/inactive_business_consumer`，不得进入任何活动构建、CI、安装、发布或运行入口。`document-provider-adapter` 必须保持在根 reactor 中，直到 02 P0 同一阶段将其移入 alpha 并以新空骨架替代。

本 blocker 关闭的是 `employee-service` → 旧 `es-query-api` 的活动 Maven 消费边，不要求在 02A 中提前改写 P0 所有的旧 Agent 入站调用。当前 `agent-adapter-employee`、`agent-service` 内对 employee 的 Feign/能力配置只可分类为 `p0_pending_legacy_caller`；`config-service/.../application-emp.yml` 分类为 `inactive_business_configuration`。两类引用在 P0 前不得被解释为可用性或生产资格，且必须由 02 P0 后续整体隔离/引用分类消除；它们存在会阻塞生产/default Agent 能力结论，但不阻塞 `CLOSED_FOR_P0_BY_INACTIVITY`。

禁止路径：`employee-service` → alpha、`employee-service` → 新空 `es-query-api`、根 reactor/profile/CI/build/install/deploy → `employee-service`、Gateway/默认启动/默认首页 → `employee-service`；也禁止本方案提前修改旧 Agent 调用方、employee 专属配置或移除 `document-provider-adapter` 的根 module。

### 7.3 内聚与耦合判断

活动资格由现有构建、启动和 Gateway 所有者分别移除，不引入兼容层、占位服务或新业务模块。退出验证集中在一个非修复脚本中，避免在多个 CI/脚本重复定义判定规则；消费者源码保持内聚且只读，后续替代设计不会被本次临时退出方案反向约束。

## 9. 条件设计章节

### 9.1 接口与兼容契约设计

本专题不修改 `employee-service` 内部 HTTP 字段、DTO 或错误模型，但通过删除 Gateway 路由和默认实例改变“默认可达性”。兼容策略是显式失败而非降级：Gateway 路径返回 404，服务发现/直连无默认实例；不新增 410 控制器、代理、重定向或占位响应。仓库外调用方和生产部署未获准核对，因此本结论只适用于仓库默认基线。

### 9.2 数据生命周期与迁移设计

`employee-service` 仍是历史员工表和相关消息处理事实的证据位置；退出 reactor/默认启动不转移数据所有权，不变更表、Topic、索引或保留周期。方案 B 没有数据迁移和回填，回滚也不操作外部数据。生产消费者停机可能引起消息积压，但生产停机不在本文授权范围，必须由未来生产变更单独评估。

### 9.3 状态、并发与一致性

实施是单工作区有序变更，不使用数据库事务或分布式锁。排他性来自干净工作区、单一实施责任人、相关进程停止和报告独占锁。每个文件动作先记录 `STARTED` 再修改，后置验证通过才记录 `COMPLETED`；中断后不能根据文件时间推断完成状态。

### 9.4 权限、安全与审计

- 实施授权必须明确接受员工表、工作流、ES API 和页面全部退出默认栈的影响。
- 验证器不读取 `.env`、凭据、业务数据、完整配置内容或生产端点。
- Gateway 删除路由会收缩暴露面，不授予新的权限或后门访问。
- 本专题审计记录操作者、HEAD、设计/授权引用、文件摘要和检查结果；P0 对该引用的消费状态只记录在 P0 报告中。两类报告均不记录员工或文档内容。

### 9.5 性能与容量

不适用生产性能目标：本专题移除能力，不承载请求。只要求严格校验和完整 reactor 构建在单次本地/CI 作业中有界完成。

### 9.6 发布、迁移与回滚

方案 B 是仓库默认基线变更，不是生产发布。实施前须停止本地 `employee-service` 实例；实施后不得启动它。P0 未开始时，经确认可按第 8.4 节逆序恢复默认首页、Gateway、启动/Eureka 和根 module，并重新验证完整 reactor。P0 开始后，消费者退出证据成为 P0 前置，必须先完成 P0 的整体恢复才能恢复这些入口。

### 9.7 日志、监控与告警

建议新增的验证器只输出结构化检查结果和稳定错误码。`CONSUMER_STILL_ACTIVE`、`RUNTIME_ENTRY_STILL_ACTIVE`、`INACTIVE_ASSET_CHANGED`、`ROLLBACK_ORDER_VIOLATION` 任一出现即退出非零；不得自动修复或降级为警告。

### 9.8 `ExternalConsumerResolutionRef` 契约

建议新增固定报告 `docs/design/agent/evidence/baseline-isolation/p0/external-consumer-resolution.json`，引用形式为仓库相对路径加报告 SHA-256。报告至少包含：

- `schemaVersion`、`resolutionId`、`chosenSolution=SCHEME_B_ACTIVE_BASELINE_EXIT`；
- `baselineCommit`、00/02/本文哈希、`authorizationRef`、`impactAcceptanceRef`；其中 `baselineCommit` 固定为完成方案 B 业务/入口变更的实施提交，不因后续文档、验证器、证据或评审报告的原子同步而改写；
- 一个 `consumers[]` 项，`name=employee-service`，及其 `reactorStatus`、`defaultStartStatus`、`gatewayStatus`、`defaultUiStatus`、`ciStatus`、`releaseStatus`、`sourceIntegrity`、`renamedToAlpha=false`；
- `referenceClassifications[]`，至少记录 `evidence_only/inactive_business_consumer`、`p0_pending_legacy_caller`、`inactive_business_configuration` 三类的路径、责任专题和允许存在期限；未知或多重分类失败；
- `checks[]`、命令/工具版本、开始/完成时间、失败码、未决项和不含报告自身的 `resultFileManifest`；
- `status=CONSUMER_EXIT_VERIFIED`、`closureSemantics=CLOSED_FOR_P0_BY_INACTIVITY`；
- `recoveryPolicy=P0_REPORT_GOVERNS`；P0 消费状态由 P0 自己的固定报告持有，本文报告发布后不可被 P0 回写。

报告不得声称 `employee-service` 已删除或改名、契约已迁移、功能已替代或生产已下线；不得把 `p0_pending_legacy_caller` 误报为已消失，也不得声称 Provider/Generation 资产已由本方案处理。首次方案 B Preflight 仍要求 `ExpectedHead` 与当时 HEAD 精确相等；固定报告重验、`PostApply` 刷新和 `RecoveryCheck` 则要求 `baselineCommit` 是当前 HEAD 的祖先，且从该提交到当前 HEAD 的 `employee-service` 提交树无变化，并同时核对当前设计哈希、`resultFileManifest`、引用分类和现场活动图。这样既保留实施提交的稳定身份，也允许后续只改变文档/证据治理的提交参与核验；祖先关系不成立返回 `DESIGN_BASELINE_CHANGED`，员工业务资产在后继提交中变化则返回 `INACTIVE_ASSET_CHANGED`。02 Preflight 还必须核对报告 SHA和当前干净 HEAD，并在 P0 自己的报告中记录外部报告路径/SHA；不能只相信文本状态。因为 02 Preflight 要求干净工作区，本次原子联动必须先经用户另行授权提交到一个新 HEAD，未提交状态不能进入 P0。

固定报告原子发布且 `status=CONSUMER_EXIT_VERIFIED`、`closureSemantics=CLOSED_FOR_P0_BY_INACTIVITY`、`unresolvedItems=[]` 时，`DB-02-001` 即关闭。02 Preflight 对该关闭事实执行只读重验：任一哈希、清单、引用分类、现场活动图或干净 HEAD 不匹配时阻塞 P0，但不得把已关闭状态改写为由 Preflight 才首次产生；现场漂移应以新的失败证据和恢复流程处理。
