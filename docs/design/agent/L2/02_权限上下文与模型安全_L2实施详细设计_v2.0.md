## 3. 设计目标与范围

目标是在最少组件内完成权限只收紧和模型边界安全；范围外如上表。最小必要抽象只增加 Auth/Policy/Projection/Model 四个内聚责任，不建设通用安全平台。

## 4. 当前实现基线、关联资源与责任边界

新 Python Agent 安全代码不存在；现有 Java `auth-service` Agent 权限接口仅是合同勘察输入。Auth 唯一负责身份/RBAC，LangGraph 的确定性安全节点负责能力/字段/语料库收紧，业务/文档源负责资源事实，模型不负责授权。

## 5. 模块职责、依赖方向与调用边界

依赖拆为两条单向链：`graph -> auth_context/result_security -> AuthClient + policy + projectors`，以及`plan/generate nodes -> ModelClient -> approved model endpoint`。确定性安全节点不得依赖或调用 ModelClient；模型节点不得调用 Auth/业务/检索 Client。禁止依赖 Java Agent 编排或旧 common-security 二进制，禁止 Auth Client 返回值直接成为最终字段授权，禁止条件边或能力节点绕过安全节点。独立 sink DTO 保持内聚并减少安全语义耦合。

## 7. 权威模型

| 事实 | 来源 | 最小字段 | Agent 处理 |
|---|---|---|---|
| 入口身份 | API 边界的 Python JWT 验证器或 Auth 内部校验合同；使用专用用户令牌验证 keyset/内省能力，不复用 Agent 服务令牌签名密钥 | `subjectRef, tenantRef?, tokenId/expiry` | 验证后写初始 State；原始 JWT 不入图，不接受网关注入头或请求体覆盖 |
| Auth 上界 | `auth-service` 内部权限解析 | `subjectRef, tenantRef, permissionCodes, allowedCapabilities/domains, evidenceVersion, validUntil` | 校验绑定和新鲜度 |
| Agent 策略 | 版本化配置 | 权限码到能力/域/字段/操作符/函数/语料库/模型用途的映射 | 只能收紧 |
| 资源事实 | 业务/文档源或检索安全标签 | tenant、资源范围、分类、版本 | 只能增加限制 |
| 请求目的 | 已校验计划 | capability/domain/operation | 不得扩展前述上界 |

有效范围计算：

```text
effective = trustedIdentity
          ∩ authUpperBound
          ∩ agentPolicy(policyVersion)
          ∩ resourceFacts(sourceVersion)
          ∩ validatedRequestPurpose
```

集合为空、未知权限码、未知字段、事实过期、tenant 不一致、版本不可验证均拒绝。不得使用默认 tenant、JWT 本地角色推断或模型补全安全事实。

## 8. 接口与契约设计：Auth 合同与调用

实施优先复核现有 `POST /internal/agent/permissions/resolve`，但目标 DTO 必须满足上节最小字段。Python Agent 在 HTTP Authorization 中使用只面向 Auth audience 的短时服务 JWT；入口 subject/tenant/tokenId 作为独立、待证明的请求字段传递，不能塞入服务 subject 或用用户 Bearer token 代替服务身份。Auth 响应必须回显已证明主体、tenant、证据版本和有效期。

Python/Java 安全兼容必须形成显式合同夹具：算法、独立 keyset/`kid`、active/previous 密钥轮换、issuer/audience、service subject、scope、签发/过期和错误码。用户令牌验证 keyset、Agent→Auth 服务令牌 keyset、模型 API 凭据三者必须逻辑和秘密隔离；不得复用用户 HMAC 签名密钥作为 Agent 服务令牌密钥。Python 只从相同秘密管理引用读取其被授权的服务密钥，不通过 HTTP/Graph State 传递。若现有合同只能通过共享宽权限用户签名密钥或不能跨语言稳定实现，PoC 必须失败并先请求 Auth 合同授权；不得改为信任 `X-USER-ID`、跳过签名或混用用户 token。

- 超时短于请求剩余预算；不持久缓存正授权；可在同一请求内复用未过期快照。
- 401/403 映射为未认证/禁止；404、未知码、5xx、超时或反序列化失败均失败关闭。
- 现存 Auth 字段级规则不是长期双权威。若目标合同仍返回旧字段，实施时必须明确只采用 Auth 上界字段，Agent 字段策略归本服务；修改 Auth 合同需单独授权并检查调用方。

## 9. 数据设计与生命周期：Agent 策略

首阶段使用受版本控制的 YAML/JSON 配置，不建设策略数据库和控制面。启动时严格校验并冻结不可变快照：

```yaml
version: "1"
permissions:
  EMPLOYEE_READ:
    capabilities: [QUERY, AGGREGATE]
    domains: [EMPLOYEE]
    filterFields: [position, workBaseSi]
    displayFields: [position, workBaseSi]
    sortFields: [position]
    groupFields: [position, workBaseSi]
    metricFields: []
    operators: [EQ, IN]
    functions: [COUNT]
corpora:
  POLICY:
    permissionCodes: [POLICY_DOCUMENT_READ]
    classification: INTERNAL
modelTargets:
  primary-model-candidate:
    enabled: false
    purposes: [PLAN, DOCUMENT_ANSWER, DOCUMENT_SUMMARY]
    maxClassification: INTERNAL
```

未知顶层项/枚举/引用、重复字段、空 target、密钥内嵌或策略放宽超过 L2 硬上限时启动失败。变更通过配置发布和服务滚动生效；首阶段不做热更新/CAS/审批数据库。生产审批流程属于发布治理，不复制到运行时策略模型。模型 target 默认`enabled: false`；只有供应商数据处理、用途、地域/保留策略和真实效果门禁全部通过后，生产配置才可启用，名称、连通性或兼容协议均不能代替批准证据。

## 10. 详细功能与核心处理流程：数据分级与最小投影

分级只用 `PUBLIC|INTERNAL|RESTRICTED|UNKNOWN`。UNKNOWN 按 RESTRICTED 处理并禁止发送外部模型。结构化字段由 Agent 策略和来源标签共同确定；原始文档由文档源给出分级。用户文本默认 INTERNAL，并经过敏感模式/长度校验；检测器不确定时不发送外部模型。

| sink | 允许 | 禁止 |
|---|---|---|
| `PLANNING` | 问题、有限历史、获准能力/字段 Schema 摘要 | JWT、权限码全集、真实数据、服务地址 |
| `SEARCH_AUTHORIZATION` | 绑定一次 Search 的 subject/tenant、逻辑索引/语料库、安全标签上界、证据版本和时效 | 用户 JWT、任意 ES 条件、模型字段、Index/Rebuild 权限 |
| `DOCUMENT_GENERATION` | 当前问题、获准证据片段、引用 ID | 未授权片段、完整文档、检索安全标签 |
| `FINAL_RESULT` | 当前范围内 DTO 字段和已验证引用 | 隐藏字段、模型额外字段、过期证据 |
| `AUDIT` | IDs 摘要、版本、枚举、数量、耗时 | 正文、Prompt、响应原文、secret |

LangGraph/ASGI/OpenTelemetry/LangSmith 等 callback 或 tracing 不得旁路 sink 投影。首版第三方 tracing 关闭；本地指标只记录节点名、耗时、结果码和数量。启用任何外发 tracing 需要字段级脱敏、供应方数据处理审批、保留期和泄漏负向测试。

每种 sink 使用独立 DTO，不以通用 Map 复用。处理顺序固定为：授权拒绝 → 字段白名单 → 分级/目的检查 → mask/drop → 数量/长度限制 → 严格序列化。`SEARCH_AUTHORIZATION`额外生成短时 compact JWS：受保护头类型固定为`agent-search-authz+jwt`，payload 使用`iss/aud/sub/iat/exp/jti`和最小授权 claims；aud 固定为 Search，sub 与独立 HTTP 服务身份 subject 一致，jti 等于 requestId，requestDigest 使用 RFC 8785 JCS 后的 SHA-256 精确绑定 logicalIndex/queryText/corpusId/filters/returnFields/page/requestId/deadlineAt（不含 JWS 自身）。它不能代替服务认证，也不能授权 Index/Rebuild。JWS 使用 Agent 服务签名 keyset 的独立 token 类型/scope，Search 按 active/previous key 校验；用户 keyset 不能签发该投影。

## 11. 模型访问

`ModelClient`输入为 `ModelRequest(purpose, targetId, messages, responseSchema, deadline)`；调用方不能提供 endpoint、API key 或任意 model name。配置将唯一 `targetId` 解析为 endpoint/model/credential reference。

每次发送前检查：target 启用、purpose/domain/分级覆盖、凭据存在、剩余 deadline 足够。失败不自动切换目标。API key 只从环境或秘密管理引用读取，不记录、不放 DTO。ModelClient 只访问配置解析出的 HTTPS 白名单目标，禁止跟随到未批准 host 的重定向。HTTP client 禁止透明写重试；明确未发送的连接失败最多一次新调用。

模型响应必须满足：HTTP/finish reason 合法、大小限制、严格 JSON Schema、未知字段拒绝、枚举/数值/字符串边界、无敏感回显。规划结果还要过 01/03/04 Validator；DOCUMENT 文本还要过引用校验和最终投影。

Prompt injection 控制以权限隔离为主：用户和检索内容都作为数据区输入；系统指令明确不得改变 capability、target、字段和授权；即使检测未命中，模型也没有 Tool/网络/数据库凭据。

## 12. 撤权与结果重验

同一同步请求内可使用未过期 Auth/策略快照。以下情况必须拒绝而非继续：Auth 快照已过 `validUntil`、tenant/主体变化、请求跨越配置版本切换且无法证明旧策略仍有效、文档来源版本/安全标签不一致。

返回前由固定 `result_security`节点以本请求当前有效范围重新投影。由于首阶段无 checkpointer、后台任务和恢复，不设计 execution fence、租约或多副本决定防重放。若以后引入持久图状态，必须先回到 L0/L1 增补 checkpoint、撤权、幂等、重放和清理设计。

## 13. 错误分类与安全审计

安全错误优先使用 `UNAUTHORIZED|FORBIDDEN|MODEL_OUTPUT_INVALID|EVIDENCE_INSUFFICIENT|UPSTREAM_UNAVAILABLE|TIMEOUT`，外部 message 保持通用。内部 `reasonCode`可区分 `SUBJECT_MISMATCH`、`TENANT_UNVERIFIED`、`POLICY_UNKNOWN`、`AUTH_EXPIRED`、`FIELD_FORBIDDEN`、`MODEL_TARGET_DENIED`、`OUTPUT_SCHEMA_INVALID`、`CITATION_INVALID`。

安全审计在所有 profile 均失败关闭，不提供“只告警仍返回结果”的运行时开关。`result_security`只有在审计接收端于剩余 deadline 内返回已接收确认后才能形成成功输出；确认语义、访问控制、保留期和删除策略必须由审计合同/生产配置冻结。开发与测试使用显式 fake/in-memory 接收端证明相同确认合同，不通过放宽失败语义绕过。审计不可用时记录独立健康指标并告警，但不能先返回敏感结果后补记。
