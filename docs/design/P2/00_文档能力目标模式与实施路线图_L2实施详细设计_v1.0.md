## 4. 背景与目标

P2 目标是把当前仓库中已有的通用文档能力骨架，收敛为可支撑以下三类用户目标的可实施设计：

1. 公司政策查询或总结。
2. 知识库查阅或总结。
3. 文献/文学资料查阅或总结。

当前代码已经存在 `AgentPlanKind.DOCUMENT`、`document.search`、`document.answer`、`document.summarize`、`DOCUMENT_RETRIEVABLE`、文档检索 Adapter、ACL filter、混合检索、证据绑定和索引治理本地门禁，但生产配置仍默认 `agent.document.enabled=false`，且缺少 `company_policy`、`knowledge_base`、`literature` 的完整 domain/corpus 配置、外部 ACL 权威源、真实 LLM/Embedding Provider 和生产级运行治理。

本文目标是定义 8 个能力详设的目标模式、依赖顺序和评审门禁，避免后续详设互相覆盖职责。

## 8. 设计边界与约束

1. 业务边界：只覆盖公司政策、知识库、文献/文学资料三类文档型查询、查阅、总结和证据绑定回答。
2. 系统边界：主要涉及 `agent-api`、`agent-service`、`agent-adapter-api`、`agent-adapter-document`、`agent-runtime`、`es-query-api`、`es-query-service`。
3. 数据边界：文档正文、chunk、embedding、ACL 投影和索引任务归文档平台/ES 查询侧；Agent Context 只保存最小检索上下文和 citation ids。
4. 权限边界：Agent 负责 capability/domain/field/result 安全边界；文档 ACL 权威源和文档平台仍是文档权限事实来源。
5. 外部系统边界：LLM、Embedding、ACL 权威源、文档平台、ES 均通过受控 Port 或 HTTP Client 接入。

## 10. 详细功能设计

### 10.1 三类业务域目标模式

| 业务域 | domain/corpus | 典型能力 | 首版要求 |
|---|---|---|---|
| 公司政策 | `company_policy` | 政策检索、条款问答、政策摘要 | 强 ACL、版本/生效日期、来源引用 |
| 知识库 | `knowledge_base` | 知识查阅、FAQ 问答、主题总结 | 标签/分类过滤、来源链接、更新时效 |
| 文献/文学资料 | `literature` | 资料查阅、证据摘录、资料总结 | 作者/标题/页码/章节、引用完整性 |

### 10.2 评审与修复策略

每份能力详设必须先执行 `detailed-design-document` 内部评审-修复循环，最大 5 轮；目标文档生成后，对 00～08 依次执行 `design-doc-review`，允许修改目标详设，最大 5 轮，不允许修改 L1 或 P1 L2 关联文档。逐份 `design-doc-review` 的关联文档规则为：上级文档使用全部 L1 架构文档；00 使用 P1 下全部 L2 详设；01～08 使用 P1 下全部 L2 详设，加 P2 下编号小于当前文档的全部详设及对应品审报告。

本地闭环与生产启用依赖必须分层记录：

1. 本地闭环依赖：允许使用 disabled port、fake provider、mock ACL 或本地 validation 骨架完成代码结构、契约和失败路径验证。
2. 生产启用依赖：真实 LLM/Embedding Provider、文档 ACL 权威源、read alias validation/rollback、审计、观测和撤权保障必须由对应 07/08 详设闭合后才能声明生产可用。
3. 04、05、06 不得把 07/08 作为已评审前置事实来源；只能把 07/08 标记为真实 Provider 或生产发布门禁。

### 10.3 进入编码门禁

任一能力进入编码前必须满足：

1. 目标详设存在文档状态、修改历史、上级约束、关联边界、实现落点、测试设计和评审记录。
2. `design-doc-review` 对该文档无 S0；若有 S1，必须先修复或明确用户接受风险。
3. 不存在需要修改 L1 或 P1 L2 文档但未授权的阻塞项。
