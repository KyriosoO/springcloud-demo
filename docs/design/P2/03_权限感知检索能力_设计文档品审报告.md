## 5. S1 严重问题

| 序号 | 位置 | 问题 | 风险 | 修改建议 |
|---:|---|---|---|---|
| 1 | 第 10.1、12、19 章 | ACL scope request 写为 `tenantId/userId/domain`，但 P1 与当前代码使用 `subjectRef/domain/permissionEvidenceId/permissionVersion/deadline` | 实施时会绕开 P1 稳定主体与权限证据链，导致 ACL client 和 Handler 契约错位 | 改为 `DocumentAclScopeRequest` 当前字段模型，`tenantId/userId` 仅作为 ACL scope 回包字段 |
| 2 | 第 11 章 | ACL HTTP 接口把路径写成配置 key，未明确 base URL、固定 path、request/response 字段及回包一致性校验 | mock server、HTTP client 和 contract test 难以对齐，回包主体/domain 不匹配时可能误放行 | 明确 `agent.document.acl.scope-url` 为 base URL，固定 path 为 `/internal/document-acl/scope/resolve`，并补 request/response 表和回包校验规则 |
| 3 | 第 16、20、21 章 | scope term 上限写成 1000，但当前 `DocumentAclFilterFactory` 本地门禁为 128 | 测试和生产容量预期不一致，可能把本地 fail closed 误判为缺陷 | 改为当前本地 128；若生产需放宽，必须配置化并补性能门禁 |
| 4 | 第 1、21、24 章 | “真实 ACL 权威源契约是编码前置”与“可作为实现依据”矛盾 | 会阻断本地闭环，或迫使修改外部契约文档而超出本任务授权范围 | 区分本地编码与生产启用：本地可按 mock/当前契约实现，生产启用前冻结真实 ACL 契约 |
| 5 | 第 10.3、19、20 章 | 用户业务 filter 不得覆盖 ACL 字段，但缺少明确实现/测试落点 | 如果 Domain Metadata 误投影 ACL 字段，用户 filter 可能干扰 ACL filter | 补充 `DocumentPlanValidator`/Domain Metadata 禁止 ACL 保护字段的实现和回归测试 |
| 6 | 第 10.4、19、20、23 章 | ResultSecurity 要求校验 domain 在 `ExecutionScope.allowedDomains`，但测试落点只覆盖 citation | 文档结果可能只按字段过滤，缺少 domain 越权回归保护 | 补充 `rejectsDomainOutsideExecutionScope` 测试和实现说明 |

以上 S1 均已在目标文档中修复，复审未发现遗留 S1。
