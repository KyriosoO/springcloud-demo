## 5. 设计目标

1. 消除 `common-security` 中 JWT HMAC secret 的硬编码。
2. 将 JWT HMAC key 与 Agent payload key 纳入统一密钥读取、校验和注入体系。
3. 保持密钥用途隔离：JWT key、Agent payload key 不共用同一把密钥。
4. 支持开发/演示环境通过配置文件注入，部署环境通过环境变量或外部 Secret 注入。
5. 支持 active/previous key，为 JWT token 兼容窗口和 Agent 历史密文解密提供轮换基础。
6. 在启动期 fail fast 校验 active key，避免请求执行到签名、验签或 Context finalization 才失败。
7. 不改变现有业务服务接口、Agent API、Runtime API、权限投影 API 和业务域表结构。

## 6. 非目标范围

| 非目标 | 说明 |
|---|---|
| 不合并密钥 | JWT HMAC key 与 Agent payload AES key 必须分开 |
| 不实现 JWE | 当前 JWT 仍是签名/验签，不做 JWT 内容加密 |
| 不接入真实 Vault/KMS SDK | 本次只定义可扩展 SPI；真实外部客户端需后续单独设计和授权 |
| 不修改业务域服务表结构 | `employee-service`、`transaction-service`、`auth-service` 业务表不变 |
| 不改变服务间 API 契约 | Authorization header、JWT claims、Agent payload contract 不因密钥来源改变 |
| 不修改 Runtime shared-key | `agent.runtime.shared-key` 可作为未来扩展项，本次只覆盖 JWT HMAC key 与 Agent payload key |

## 7. 现状与问题

### 7.1 JWT HMAC key 现状

`common-security/src/main/java/com/dylan/common/security/JwtConfig.java` 当前使用硬编码常量：

```java
private static final String SECRET = "my-super-secret-key-my-super-secret-key";
```

并基于该值创建 `SecretKeySpec(SECRET.getBytes(), "HmacSHA256")`，供 `JwtEncoder`、`JwtDecoder`、`ReactiveJwtDecoder` 和 `ServiceTokenProvider` 使用。

问题：

1. 密钥进入代码仓库，违反密钥不入库原则。
2. 所有环境共用同一默认密钥，无法按环境隔离。
3. 缺少 active/previous key 轮换语义。
4. 缺少启动期强校验和配置来源审计。

### 7.2 Agent payload key 现状

`agent-service` 当前通过 `EnvironmentPayloadKeyProvider` 从 `System.getenv()` 读取：

```text
AGENT_PAYLOAD_KEY_<KEY_ID>
```

当前 bootstrap 中 active key id 为 `ACTIVE`，因此本地必须提供：

```text
AGENT_PAYLOAD_KEY_ACTIVE
```

问题：

1. 只能从环境变量读取，不支持开发/演示配置文件注入。
2. 缺少统一 Secret 入口，JWT 与 payload key 管理方式不一致。
3. 当前实现可能在加密时才暴露缺失 key，启动期 fail fast 不完整。
4. D02_03 正式文档只描述 `EnvironmentPayloadKeyProvider`，与本需求不完全一致。

## 8. 总体方案

新增统一密钥管理抽象，按“统一入口、用途隔离、多来源解析、启动校验、轮换兼容”设计。

```text
应用配置 / 环境变量 / 外部 Secret
          |
          v
SecretMaterialProvider
  |- ConfigSecretMaterialProvider      # dev/demo
  |- EnvironmentSecretMaterialProvider # deployment
  `- CompositeSecretMaterialProvider   # 按配置顺序选择来源
          |
          v
用途适配层
  |- JwtKeyProvider                    # HMAC-SHA256 signing/verification
  `- PayloadKeyProvider                # AES-256-GCM payload encryption
          |
          v
现有消费方
  |- JwtEncoder / JwtDecoder / ReactiveJwtDecoder / ServiceTokenProvider
  `- AeadProtectedPayloadCodec
```

关键原则：

1. Secret 管理入口统一，但 key namespace 分离。
2. 开发/演示可使用配置文件明文注入；生产必须禁用配置文件明文 key。
3. 所有 key value 只在内存中存在，不输出到日志、错误、Actuator 或配置打印。
4. active key 用于新签名/新加密，previous key 仅用于兼容旧 token 或历史密文解密。
5. 启动时必须校验 active key 可解析、长度与算法匹配。

## 9. 配置设计

### 9.1 统一配置模型

新增配置前缀：

```yaml
common:
  security:
    secrets:
      source-order: [environment, config]
      allow-config-values: false
      fail-fast: true
      jwt:
        active-key-id: active
        previous-key-ids: []
        keys:
          active:
            env: COMMON_SECURITY_JWT_HMAC_KEY_ACTIVE
            value: ""
      agent-payload:
        active-key-id: active
        previous-key-ids: []
        keys:
          active:
            env: AGENT_PAYLOAD_KEY_ACTIVE
            value: ""
```

### 9.2 开发/演示环境配置

开发/演示 profile 允许配置文件注入，但必须使用明显的非生产样例值：

```yaml
common:
  security:
    secrets:
      allow-config-values: true
      source-order: [config, environment]
      jwt:
        active-key-id: dev
        keys:
          dev:
            value: "base64-32-byte-dev-hmac-key"
      agent-payload:
        active-key-id: dev
        keys:
          dev:
            value: "base64-32-byte-dev-aes-key"
```

约束：

- dev/demo 样例值不得用于生产。
- 样例值可以进入本地文档，但不得把真实生产密钥写入 Git。
- 启动日志只允许输出 key id、source type、用途和校验状态，不输出 value。

### 9.3 部署环境配置

生产和类生产环境必须使用环境变量或外部 Secret 注入：

```powershell
$env:COMMON_SECURITY_JWT_HMAC_KEY_ACTIVE = "<Base64-32-byte-hmac-key>"
$env:AGENT_PAYLOAD_KEY_ACTIVE = "<Base64-32-byte-aes-key>"
```

部署规则：

1. `common.security.secrets.allow-config-values=false`。
2. `source-order` 必须以 `environment` 或未来 `external` 为优先来源。
3. 配置文件只保存 key id、env var 名称和策略，不保存真实 key value。

## 10. 数据结构设计

### 10.1 `SecretPurpose`

| 字段 | 类型 | 说明 |
|---|---|---|
| `JWT_HMAC` | enum | JWT HS256 签名/验签用途 |
| `AGENT_PAYLOAD` | enum | Agent Context/Result payload AES-GCM 加解密用途 |

### 10.2 `SecretKeyRef`

| 字段 | 类型 | 说明 |
|---|---|---|
| `purpose` | `SecretPurpose` | 密钥用途 |
| `keyId` | `String` | 稳定 key id，只允许 `[A-Za-z0-9_]{1,64}` |
| `envName` | `String` | 可选环境变量名 |
| `configValue` | `String` | 可选配置文件值，仅 dev/demo 可用 |

### 10.3 `SecretMaterial`

| 字段 | 类型 | 说明 |
|---|---|---|
| `purpose` | `SecretPurpose` | 密钥用途 |
| `keyId` | `String` | key id |
| `secretValue` | `SecretValue` | 解码后的密钥字节包装，禁止默认 `toString()` 泄露 |
| `source` | `SecretSourceType` | `ENVIRONMENT` / `CONFIG` / `EXTERNAL` |

`SecretMaterial` 不使用 Java record 直接保存 Base64 明文字段，避免 record 自动生成的 `toString()`、日志或调试输出泄露密钥。实现必须使用 final class 或显式覆盖 `toString()` 返回脱敏文本，并通过防御性复制向下游提供密钥字节。

### 10.4 `SecretValue`

| 字段 | 类型 | 说明 |
|---|---|---|
| `raw` | `byte[]` | 解码后的密钥字节，构造和读取均防御性复制 |

方法约束：

- `byte[] copyBytes()` 返回密钥字节副本，调用方创建 `SecretKeySpec` 后不得继续日志化或序列化；
- `String toString()` 固定返回 `[REDACTED]`；
- 不提供返回 Base64 原文的 getter；
- 可选实现 `destroy()` 清零内部数组，但不得依赖 GC 或日志过滤作为唯一保护。

### 10.5 `JwtKeySet`

| 字段 | 类型 | 说明 |
|---|---|---|
| `activeKeyId` | `String` | 签发新 JWT 使用的 key id |
| `activeKey` | `SecretKey` | HMAC-SHA256 active key |
| `verificationKeys` | `Map<String, SecretKey>` | 验签 key 集合，包含 active 和 previous |

### 10.6 `AgentPayloadKeySet`

| 字段 | 类型 | 说明 |
|---|---|---|
| `activeKeyId` | `String` | 新 payload 加密使用的 key id |
| `encryptionKey` | `SecretKey` | AES-256 active key |
| `decryptionKeys` | `Map<String, SecretKey>` | 历史密文解密 key 集合 |

## 11. Java 接口设计

### 11.1 统一 Secret 读取端口

```java
public interface SecretMaterialProvider {
    SecretMaterial requireSecret(SecretKeyRef ref);
}
```

语义：

- 找不到密钥时抛 `SecretMaterialException`；
- 异常不得包含密钥值；
- 返回值不得暴露到日志或 API；
- 支持按 `source-order` 决定解析顺序。

### 11.2 JWT key provider

```java
public interface JwtKeyProvider {
    JwtKeySet current();
}
```

语义：

- `current().activeKey()` 用于 `JwtEncoder`；
- `current().verificationKeys()` 用于 `JwtDecoder` 和 `ReactiveJwtDecoder`；
- JWT 签发必须在 JWS header 写入 active key id 的 `kid`；
- JWT 验签必须按 token header `kid` 从 active + previous key 集合中选择 key；
- 缺失 `kid` 的存量 token 默认拒绝；如实施阶段确需兼容，必须增加显式过渡开关、TTL 截止时间和测试覆盖，且不得作为长期默认行为。

### 11.3 Agent payload key provider

继续复用现有端口：

```java
public interface PayloadKeyProvider {
    SecretKey requireKey(String keyId);
}
```

改造点：

- 现有 `EnvironmentPayloadKeyProvider` 保留为兼容实现或测试辅助；
- 新增 `SecretMaterialPayloadKeyProvider`，通过 `SecretMaterialProvider` 读取 `AGENT_PAYLOAD` namespace；
- `AeadProtectedPayloadCodec` 不修改算法和 AAD 语义。

## 12. 核心流程设计

### 12.1 应用启动

```text
Spring Boot bind properties
  -> SecretPropertiesValidator.validate()
  -> SecretSanitizingConfiguration registers actuator sanitizing keys
  -> JwtKeyProvider.current()
  -> PayloadKeyProvider.requireKey(activePayloadKeyId)
  -> JwtEncoder/JwtDecoder/ProtectedPayloadCodec beans ready
```

失败规则：

| 场景 | 行为 |
|---|---|
| active key id 为空 | 启动失败 |
| key id 格式非法 | 启动失败 |
| active key 缺失 | 启动失败 |
| Base64 非法 | 启动失败 |
| JWT key 长度不足 32 bytes | 启动失败 |
| payload key 解码后不是 32 bytes | 启动失败 |
| prod 启用配置文件明文 key | 启动失败 |
| Actuator 脱敏规则未覆盖密钥配置前缀 | 启动失败或禁止暴露 env/configprops endpoint |

### 12.2 JWT 签发

```text
AuthController.login
  -> JwtService.generateToken
  -> JwtKeyProvider.current().activeKeyId
  -> JwsHeader(kid=JwtKeyProvider.activeKeyId)
  -> JwtEncoder
  -> JwtKeyProvider.activeKey
  -> HS256 signed JWT
```

说明：

- JWT payload 不加密；
- 签名 key 只保证 token 完整性和来源可信；
- `JwtService` 和 `ServiceTokenProvider` 必须注入 `JwtKeyProvider`，不能通过硬编码或重复读取配置获得 `kid`；
- `JwtService.generateToken` 和 `ServiceTokenProvider` 均必须设置 JWS header `kid`；
- 本文不改变 claims、TTL、role、scope 结构。

### 12.3 JWT 验签

```text
Resource Server receives Authorization: Bearer
  -> KidAwareJwtDecoder reads JWS header kid
  -> JwtKeyProvider.verificationKeys
  -> select key by kid
  -> verified Jwt
```

说明：

- `kid` 命中 active 或 previous 时可验签；
- `kid` 不存在、未知或对应 key 不存在时认证失败；
- 认证失败日志只记录 failure reason 和 diagnosticId，不记录 token 原文。

### 12.4 Agent payload 加密

```text
ContextFinalizationParticipantImpl.persist
  -> PayloadJsonCodec.serialize
  -> AeadProtectedPayloadCodec.encrypt
  -> PayloadKeyProvider.requireKey(activePayloadKeyId)
  -> ProtectedPayload(ciphertext, keyId, nonce, algorithmVersion)
```

不变项：

- AES-256-GCM；
- 96-bit nonce；
- `PayloadProtectionContext` AAD；
- key rotation 不改变 ContractRef/schema；
- 解密/tag 校验失败 fail closed。

### 12.5 Agent payload 解密

```text
ContextBoundary.load
  -> repository reads ProtectedPayload
  -> reconstruct PayloadProtectionContext from DB authority columns
  -> AeadProtectedPayloadCodec.decrypt
  -> PayloadKeyProvider.requireKey(payload.keyId)
```

说明：

- 历史 key 必须保留到历史密文过期或迁移完成；
- 不允许 active key 切换后删除仍被历史密文引用的 key。

### 12.6 Agent metadata digest

`DefaultAgentMetadataBootstrap` 构建 `AgentMetadataBundle` 时，bundle digest 必须覆盖会影响 Context/Result 安全语义的字段：

- `AgentSecuritySettings.activePayloadKeyId`；
- `globalMaxContextTtl`；
- `contextCleanupDelay`；
- `contextCleanupBatchSize`；
- 其他已纳入 D02_03 的 Profile/Policy/Context/Security 语义字段。

active payload key id 不得只存在于普通 `AgentProperties` 且绕过 `AgentMetadataBundle` digest。实施时应将该字段收敛到 metadata security settings 或由 `AgentMetadataProperties` 明确映射，确保 active key id 变化触发 reload 校验、bundle 变更和后续加密 key 切换。

## 13. 状态与轮换设计

### 13.1 JWT key 轮换

| 阶段 | active | previous | 行为 |
|---|---|---|---|
| 初始 | `jwt-v1` | 空 | 签发和验签都使用 `jwt-v1` |
| 过渡 | `jwt-v2` | `jwt-v1` | 新 token 用 `jwt-v2`，旧 token 在 TTL 内可验 |
| 完成 | `jwt-v2` | 空 | 旧 token TTL 结束后移除 `jwt-v1` |

### 13.2 Agent payload key 轮换

| 阶段 | active | previous | 行为 |
|---|---|---|---|
| 初始 | `payload-v1` | 空 | 新密文和历史密文均用 `payload-v1` |
| 过渡 | `payload-v2` | `payload-v1` | 新密文用 `payload-v2`，旧密文按密文 keyId 解密 |
| 清理 | `payload-v2` | 空 | 确认所有 `payload-v1` 密文过期或已迁移后移除 |

## 14. 异常处理设计

| 异常 | 触发条件 | 对外行为 | 内部日志 |
|---|---|---|---|
| `SecretMaterialException` | 密钥缺失、Base64 非法、长度错误 | 启动失败或安全失败 | 只记录 purpose、keyId、source、diagnosticId |
| `IllegalStateException` | codec 加解密失败 | fail closed，不返回成功 | 不记录 payload、密钥值 |
| `JwtException` | token 签名无效或过期 | 认证失败 | 不记录 token 原文 |
| 配置策略违规 | prod 配置明文 key | 启动失败 | 记录配置 key，不记录 value |

## 15. 授权、风控与审计设计

1. 密钥读取不参与业务授权判断，不替代 `UserPermissionAuthorityPort`。
2. JWT key 只用于认证 token 签名/验签，不作为 Agent 权限事实来源。
3. Agent payload key 只用于 `ProtectedPayload` 加解密，不扩散到业务服务。
4. 审计日志只记录 key id、purpose、source type、校验结果和 diagnosticId。
5. 不允许把密钥值写入配置导出、错误响应、Actuator、trace、metrics label、SQL 或审计事件。

## 16. 幂等、事务与一致性设计

| 领域 | 设计 |
|---|---|
| JWT 签发 | 无数据库事务；active key 切换后新 token 使用新 key |
| JWT 验签 | 在 TTL 兼容窗口内可接受 active + previous key |
| Context finalization | 保持 D02_02/D02_03 原事务语义；加密失败整体回滚，不返回 SUCCESS |
| Payload 解密 | 按密文 keyId 解析 key；active key 切换不影响历史密文 |
| Secret reload | 本阶段不设计热 reload；修改密钥后重启服务生效 |

## 17. 性能与容量设计

1. Secret 解析在启动期和 key set 构建时完成，运行期不频繁读取环境变量或配置。
2. `JwtKeySet` 和 payload key 可在 provider 内以不可变对象缓存。
3. 不在 metrics label 中放 key id 以外的高基数或敏感值。
4. AES-GCM 和 HMAC 操作保持现有复杂度，密钥来源统一不会成为请求路径瓶颈。

## 18. 兼容与扩展设计

| 扩展点 | 当前实现 | 后续扩展 |
|---|---|---|
| Secret 来源 | config、environment | Vault/KMS/云 Secret Manager |
| JWT 算法 | HS256 | 后续可设计 RS256/JWKS，不在本次范围 |
| JWT 多 key 验签 | 基于 `kid` 支持 active + previous | 后续可扩展为 JWKS/JWT processor |
| Payload key | AES-256 | 保持 AES-256-GCM，不改变密文结构 |
| Runtime shared-key | 不纳入本次 | 后续可接入同一 SecretMaterialProvider |

## 19. 日志、监控与告警

### 19.1 日志

允许记录：

- `purpose`;
- `keyId`;
- `sourceType`;
- `validationStage`;
- `diagnosticId`;
- `errorCode`。

禁止记录：

- Base64 key value；
- JWT token 原文；
- Context/result payload；
- 环境变量值；
- 配置文件中的密钥值。

### 19.2 Actuator 与配置导出脱敏

实现必须覆盖 Spring Boot Actuator `env`、`configprops` 和内部诊断配置输出：

| 项 | 要求 |
|---|---|
| 脱敏前缀 | `common.security.secrets.*`、`*.secret*`、`*.password*`、`*.token*`、`*.key*` |
| 环境变量模式 | `COMMON_SECURITY_JWT_HMAC_KEY_*`、`AGENT_PAYLOAD_KEY_*` |
| 配置值字段 | `common.security.secrets.*.value` 必须显示为 `******` 或 `[REDACTED]` |
| 失败策略 | 无法确认脱敏生效时，生产 profile 禁止暴露 `env`/`configprops` |

若项目使用 Spring Boot `SanitizingFunction`，新增 `SecretSanitizingConfiguration` 注册统一脱敏规则；若只使用配置项，必须设置 `management.endpoint.env.keys-to-sanitize` 与 `management.endpoint.configprops.keys-to-sanitize`，并通过测试证明真实 key value 不会出现在响应体。

### 19.3 指标

| 指标 | 类型 | 标签 | 说明 |
|---|---|---|---|
| `security.secret.validation.count` | counter | `purpose`,`result` | 启动期密钥校验结果 |
| `security.secret.source.count` | counter | `purpose`,`source` | 密钥来源统计，不含 value |
| `security.jwt.decode.failure.count` | counter | `reason` | JWT 验签失败 |
| `agent.payload.crypto.failure.count` | counter | `operation` | payload 加解密失败 |

### 19.4 告警

1. 生产环境出现 config value source 时告警并启动失败。
2. JWT 验签失败率异常升高时告警。
3. payload 解密失败出现非零持续增长时告警。

| 1 | JWT 存量 token | 历史 token 可能没有 `kid` | 兼容切换期内旧 token 默认验签失败 | 本设计默认拒绝缺失 `kid`；如需兼容必须显式开关、TTL 截止时间和测试，不作为默认行为 | 否 |
| 2 | 配置泄露 | dev/demo 允许配置文件 key，可能误提交真实 key | 泄露认证和 payload 密钥 | 使用样例值、扫描规则和 prod 禁用校验 | 否 |
| 3 | 历史密文 | payload previous key 删除过早会导致历史 Context 解密失败 | Agent 历史上下文不可读 | 删除 previous key 前先确认 TTL 过期或完成迁移 | 否 |
| 4 | Bean 注入 | `SecretKey` Bean 被 JWT 与 payload 混用 | 用途隔离失效 | payload 不暴露通用 `SecretKey` Bean，只通过 `PayloadKeyProvider` | 否 |
| 5 | 部署差异 | 不同服务配置 key id 不一致 | JWT 跨服务验签失败 | 部署清单统一声明 `COMMON_SECURITY_JWT_HMAC_KEY_ACTIVE` | 否 |
