## 4. 背景与目标

旧 P2 已形成文档能力本地闭环：`DocumentRetrievalRequest`、`DocumentAgentAdapter`、`DocumentRetrievalMapper`、`EsDocumentService.hybridSearch(...)`、`HybridSearchMerger`、ACL filter、`dense_vector` mapping 校验和证据绑定能力均已存在。当前差距是检索能力仍以 `KEYWORD/VECTOR/HYBRID` 为中心，缺少资料域/资料类型可配置 profile、BM25/exact/phrase/dense_vector 多通道召回、N 路 RRF、文档级去重、rerank 接入点和 gold query 诊断。

本设计目标是在不修改 L0/L1 核心架构边界的前提下完成以下升级：

1. Java 侧统一负责问题改写候选接收、规则抽取、关键词增强、元数据过滤、召回编排、RRF、文档级去重、rerank、权限过滤和最终执行计划。
2. Runtime 只参与 LLM 改写候选，不生成 ES DSL、不选择索引、不生成权限过滤、不决定最终执行计划。
3. 支持 `domain + materialType + retrievalProfile + indexAlias` 配置，覆盖税务政策、公司政策、国家法律、通知、办法、问答等资料类型。
4. ES 查询从当前 keyword/vector 双路扩展为 BM25、exact/phrase、dense_vector 多路召回。
5. 通过 N 路 RRF、document-level 去重和可选 rerank 提升 TopK 质量，并输出可诊断字段。

## 6. 上级文档约束

| 上级约束 | 本设计承接方式 |
|---|---|
| Java 是结构契约和执行权威 | 新增 profile、召回通道、RRF、rerank 都从 Java DTO/配置开始，Runtime 输出只作为候选 |
| Runtime 不可信 | Runtime 不接收 ACL scope、ES index alias、mask 规则、完整 metadata，不返回 DSL 或执行计划 |
| capabilityId 是授权、路由、执行和审计主键 | 不新增 capabilityId；仍使用 `document.search`、`document.answer`、`document.summarize` |
| 新 Domain 不修改 Agent 主流程 | 新资料域通过 Domain Metadata/profile/index alias 配置扩展，不修改 Planning/Core 主流程 |
| Adapter 是业务域公开边界 | Agent Core 不直接依赖 ES client；通过 `DocumentRetrievableAdapter` 与 `DocumentSearchClient` 进入 es-query-service |
| ResultSecurity 是输出安全边界 | 检索结果进入用户响应前继续经过 `DocumentResultSecurityProjector` |

## 8. 设计边界与约束

1. 业务边界：首版以文档检索、问答和摘要前置证据召回为主，不新增写操作。
2. 模块边界：`agent-api` 承载公共 plan option；`agent-adapter-api` 承载 Java 校验后的检索请求；`agent-service` 负责 profile 解析、改写候选校验、embedding/rerank Port；`agent-adapter-document` 负责请求映射和下游调用；`es-query-service` 负责 ES 通道执行、RRF、去重和上下文窗口。
3. 数据边界：ES hit metadata、embedding、queryVector、ACL scope 不进入 Runtime 和用户响应；只输出安全诊断摘要。
4. 权限边界：所有通道必须共享业务 filter 与 ACL filter；缺少 ACL filter 的 document index 查询 fail closed。
5. 兼容边界：新增字段必须为可选字段，默认映射到现有 HYBRID 行为；旧 KEYWORD/VECTOR/HYBRID 请求仍可工作。
6. 扩展边界：新增资料域或资料类型只新增配置/profile/index alias，不复制 Java 流程。

## 9. 总体设计

```mermaid
flowchart LR
    A["Runtime候选Plan"] --> B["DocumentPlanValidator"]
    B --> C["DocumentRetrievalProfileResolver"]
    C --> D["DocumentQueryPreparationService"]
    D --> E["DocumentEmbeddingPort"]
    D --> F["DocumentRetrievalRequest"]
    F --> G["DocumentAclScopePort"]
    G --> H["DocumentAgentAdapter"]
    H --> I["DocumentRetrievalMapper"]
    I --> J["HybridSearchRequest.channels"]
    J --> K["DocumentSearchClient.hybridSearch"]
    K --> L["EsDocumentService.hybridSearch"]
    L --> M["BM25 / EXACT / PHRASE / VECTOR"]
    M --> N["HybridSearchMerger N路RRF"]
    N --> O["DocumentDeduplication"]
    O --> P["DocumentEvidenceMapper"]
    P --> Q["AdapterDocumentResult"]
    Q --> R["DocumentCapabilityHandler.applyRerankIfEnabled"]
    R --> S["ResultSecurity"]
```

核心原则：Java 先把 Runtime 候选计划转成可信 `DocumentRetrievalRequest`，再由 adapter 生成扩展后的 `HybridSearchRequest`。ES 服务只执行已授权通道和 filter，不自行选择 domain、materialType、profile 或 ACL。

## 10. 详细功能设计

### 10.1 检索 profile 解析

#### 10.1.1 功能说明

`DocumentRetrievalProfileResolver` 根据 `domain`、`materialType`、显式 `retrievalProfile` 和 `AgentProperties.DocumentProperties` 解析有效 profile。

#### 10.1.2 输入与输出

| 输入 | 类型 | 说明 |
|---|---|---|
| `domain` | String | 来自 Java domain projection |
| `materialType` | String | 可选，来自 plan options 或 Java 规则抽取 |
| `retrievalProfile` | String | 可选，来自 plan options；必须在配置 allowlist 内 |
| `RetrievalProfileProperties` | object | 字段权重、通道、alias、rerank 和去重配置 |

| 输出 | 类型 | 说明 |
|---|---|---|
| `DocumentRetrievalProfile` | Java value object | 有效 profile 快照，进入 `DocumentRetrievalRequest` |

#### 10.1.3 业务规则

1. 显式 `retrievalProfile` 优先级高于 `domain + materialType` 默认映射，但必须属于该 domain 允许的 profile。
2. 无 materialType 时使用 domain 默认 profile。
3. 配置缺失或 profile 不存在时 fail closed，不退回硬编码默认索引。
4. profile 必须声明至少一个召回通道；启用 `DENSE_VECTOR` 时必须允许 embedding。
5. profile 的 `indexAlias` 必须与 `agent.document-adapter.index-by-domain` 或 V2 profile 显式 alias 一致。

### 10.2 Java 侧查询准备

#### 10.2.1 功能说明

`DocumentQueryPreparationService` 在 Java 内完成规则抽取和候选改写归一化。

#### 10.2.2 处理流程

1. 接收原始 `queryText`。
2. 使用正则/词典抽取文号、日期、机关、税种、有效性、资料类型等结构化条件。
3. 生成 Java 可信 `metadataFilters`，与用户 filter 合并前先校验字段权限。
4. 接收 Runtime 或外部 LLM 改写候选时，只作为 `rewriteCandidates`。
5. Java 对候选执行长度、字符集、重复、敏感信息、domain/profile 一致性校验。
6. 构造用于 BM25/exact/phrase/vector 的 query variants。

#### 10.2.3 约束

Runtime 候选不能直接进入 DSL。Java 必须重新计算通道、filter、indexAlias、topK、RRF 和 rerank 输入。

### 10.3 多路召回请求

#### 10.3.1 通道定义

| 通道 | 枚举 | ES 查询目标 | 典型用途 |
|---|---|---|---|
| BM25 | `BM25` | `multi_match` / `match` | 通用关键词召回 |
| 精确 | `EXACT` | `term` / `terms` on `.keyword` | 文号、标题、机关、税种、资料类型 |
| 短语 | `PHRASE` | `match_phrase` | 条款、完整问题、政策短句 |
| 向量 | `DENSE_VECTOR` | `knn` | 语义召回 |

#### 10.3.2 处理规则

1. `DocumentRetrievalMapper.toHybridRequest(...)` 根据 profile 生成带 `channels` 的 `HybridSearchRequest`。
2. 每个 `HybridSearchChannelRequest` 必须包含 `channel`、`k`、`queryDsl` 或 `queryVector`、`embeddingField`、`weight` 等结构化字段。
3. 所有通道共享 `filters`，不得由通道单独覆盖 ACL filter。
4. ES 返回每一路的 raw hits，由 `HybridSearchMerger.merge(channelHits, request)` 执行 N 路 RRF。
5. 缺失 queryVector 时不得执行 `DENSE_VECTOR`；如果 profile 要求 vector 为必需则 fail closed，否则降级并记录诊断。

### 10.4 N 路 RRF 与文档级去重

#### 10.4.1 RRF 公式

```text
rrfScore(documentOrChunk) = sum(channelWeight_i / (rrfK + rank_i))
```

`rank_i` 为命中在第 i 个召回通道中的排序，从 1 开始。

#### 10.4.2 去重规则

1. 首先按 `chunkId` 聚合同一 chunk 的多通道命中。
2. RRF 排序后，按 `documentId` 执行文档级去重，默认每个文档最多保留 `maxChunksPerDocument=1`。
3. `documentLevelTopK` 结果不足时，可从同文档下一 chunk 补位，但不得超过 profile 上限。
4. RRF/去重阶段 tie-break 顺序为：`rrfScore desc`、`bestRank asc`、`channelCount desc`、`documentId asc`、`chunkIndex asc`；`rerankScore` 只能在 rerank 成功后参与最终排序。
5. 每个 hit 保留 `retrievalChannels`、各通道 rank、原始最高分、RRF 分、去重原因。

### 10.5 可选 rerank

1. `DocumentRerankPort` 位于 `agent-service`，默认实现 `DisabledDocumentRerankPort` 原样返回。
2. `es-query-service` 只负责多通道召回、RRF、文档级去重和上下文窗口，不直接调用 rerank Provider。
3. `DocumentCapabilityHandler.applyRerankIfEnabled(...)` 在 `DocumentAgentAdapter.retrieve(...)` 返回 `AdapterDocumentResult` 后执行 rerank；rerank 后再进入 generation evidence selection、citation verification 和 ResultSecurity。
4. rerank 输入只能是 RRF 和文档级去重后的候选，不接收完整 ACL scope、queryVector 或未过滤 metadata。
5. rerank 结果必须包含 candidate id、score、reason code，不允许直接生成最终答案。
6. rerank 超时、失败或关闭时走 RRF 结果，并记录 `rerankSkippedReason`。
7. 生产接入外部 rerank 服务需要单独授权，不在本次引入新依赖。

### 10.6 ES v2 索引与 alias

1. `agent-doc-<domain>-v2` 物理索引使用 read alias 暴露给 adapter。
2. v2 mapping 必须包含 `domain`、`materialType`、`retrievalProfile`、`documentId`、`chunkId`、`chunkIndex`、`title`、`content`、`snippet`、`section`、`issuer`、`taxType`、`documentNo`、`effectiveDate`、`validityStatus`、ACL 字段和 `embedding`。
3. analyzer 可按 profile 区分，例如税务政策启用政策文号/机关/税种相关 analyzer，公司政策启用组织词典。
4. alias 切换仍复用 P2 01 的 `AliasSwitchRequest`、validation digest 和 rollback 门禁。

| API | 方法 | 路径 | 请求 | 响应 |
|---|---|---|---|---|

## 12. 数据设计

```yaml
agent:
  document:
    retrieval-profiles:
      tax_policy_default:
        domain: tax_policy
        material-types: [policy, notice, faq]
        index-alias: agent-doc-tax-policy-read
        channels:
          - channel: EXACT
            size: 20
            fields: [documentNo.keyword, title.keyword, issuer.keyword]

            size: 20
            fields: [title^3, content, section]

            size: 40
            fields: [title^3, snippet^2, content, section]
```

## 13. 状态流转设计

| 状态 | 触发条件 | 处理 |
|---|---|---|
| `PROFILE_RESOLVED` | Java 根据 domain/materialType 解析 profile 成功 | 冻结 profile snapshot |
| `QUERY_PREPARED` | 规则抽取和候选改写校验完成 | 生成 query variants 和 metadata filters |
| `CHANNELS_PLANNED` | profile 通道裁剪完成 | 生成 `HybridSearchRequest.channels` |
| `CHANNELS_EXECUTED` | ES 多通道返回 | 进入 RRF |
| `FUSED` | N 路 RRF 完成 | 进入 document-level 去重 |
| `DEDUPED` | 文档级去重完成 | 按配置进入 rerank 或返回 |
| `RERANKED` | rerank 成功 | 返回最终候选 |
| `DEGRADED` | 可选通道失败 | 记录诊断，继续可用通道 |
| `FAILED_CLOSED` | 必需通道、ACL、profile、alias 缺失 | 抛错，不返回不可信结果 |

## 14. 幂等、事务与一致性设计

1. 检索不写业务数据，不涉及数据库事务。
2. 同一 query、profile、alias、ACL filter、queryVector 和 ES 索引版本下，RRF 与去重排序必须稳定。
3. profile snapshot 在单次 invocation 内不可变，避免 reload 导致同一请求前后策略不一致。
4. alias 切换期间只读 alias 是权威入口，不访问写入中的物理索引。
5. rerank 失败不改变 ES 结果，只影响排序增强；默认降级到 RRF。

## 15. 权限、风控与审计设计

1. `DocumentAclScope` 仍由 Java 在执行前解析并注入。
2. `DocumentAclFilterFactory.build(...)` 生成的 filter 必须传入 `HybridSearchRequest.filters`。
3. `EsDocumentService.hybridSearch(...)` 对 document index 缺少 filters 的请求 fail closed。
4. profile 不允许配置绕过 ACL 的通道。
5. 审计日志记录 `invocationId/domain/materialType/profile/channels/topK/rrfK/dedup/rerankEnabled/degradedReason`，禁止记录完整 queryVector、content、ACL scope 列表和 embedding。

## 16. 性能与容量设计

| 项目 | 目标 |
|---|---|
| 默认通道数 | 3～4 个 |
| 单通道候选上限 | 默认 40，最大 200 |
| RRF 候选上限 | 默认 100，最大 500 |
| rerank 候选上限 | 默认 20，最大 50 |
| 默认 topK | 5～20，受 `AgentProperties.DocumentProperties.maxSize` 和 domain maxPageSize 约束 |
| 降级策略 | 可选通道失败可降级；必需通道失败 fail closed |
| 超时策略 | 遵守 invocation absolute deadline；rerank 使用剩余预算且默认关闭 |

## 17. 兼容性与扩展性设计

1. `DocumentRetrievalOptions` 新字段可选；旧请求不携带时按 domain 默认 profile 解析。
2. 旧 `HybridSearchRequest` 和 `/hybrid-search` 保留，避免一次性删除旧测试路径。
3. 新资料域只新增 domain metadata、profile 配置、index alias 和可选 analyzer/mapping。
4. 新召回通道只新增 `RetrievalChannelType` 和 `ChannelExecutor`，不改 Handler/Adapter 入口。
5. 新 rerank Provider 只实现 `DocumentRerankPort`，不侵入 ES 查询服务。
